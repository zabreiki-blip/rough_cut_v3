# Проверка распознавания, сопоставления и нормализации — 21 октября 2026

Главный вывод: составные реплики уже частично поддерживаются, но система ищет каждый фрагмент отдельно и не проверяет качество всей сборки. Наибольшую пользу дадут совместный выбор фрагментов и уточнение временных границ. Замена ASR-модели сама по себе эти ограничения не исправит.

Проверка выполнена по текущему коду, существующим тестам и синтетическим примерам. Исходный код не изменён. Реальные записи не прослушивались, платное распознавание не запускалось; проценты улучшения качества или скорости не измерялись.

**Что уже работает**

- Stage 1 выделяет фрагменты по явным таймкодам и пометкам `СКЛ` / `СКЛЕЙКА`: `src/stage1/normalizer.py:1907–1992`.
- Stage 2 дополнительно делит синхрон по предложениям и многоточиям: `src/stage2/timeline_parser.py:73–174`. API создаёт отдельные единицы поиска: `src/api.py:1273–1326`. Таким образом, один блок сценария уже может собрать несколько клипов, в том числе из разных источников.
- Есть фильтрация источников по спикеру, альтернативы совпадений и проверка смысловых расхождений в числах и отрицаниях: `src/stage2/sync_matcher.py:1320–1448,1572–1588`.
- Есть кэш распознавания и моделей, предварительная подготовка токенов, ограничение поиска кандидатов, повторное распознавание обнаруженных пропусков облачной ASR. Эти механизмы следует развивать, а не создавать заново.

**Подтверждённые проблемы и ограничения**

1. **Высокий приоритет: совпадение текста может захватить огромную паузу.**

   Оценка сходства сравнивает токены без штрафа за разрывы во времени (`src/stage2/sync_matcher.py:515–542`). Границы кандидата берутся от первого до последнего слова (`:1042–1054`).

   Воспроизведение: «мы обязательно» находится на 10.0–10.6 с, «вернемся завтра» — на 900.0–900.7 с. Запрос «мы обязательно вернемся завтра» получает `auto_matched`, `confidence=1.0`, речевой диапазон 10.0–900.7 с, монтажный диапазон с отступами 8.0–902.2 с.

   Исправление: учитывать межсловные разрывы, реальную активность речи и длительность кандидата. При подозрительном разрыве предлагать два фрагмента либо ручную проверку. Порог паузы нужно подобрать на реальных интервью; он не должен автоматически считать любую естественную паузу монтажной склейкой.

2. **Высокий приоритет: нет совместного выбора кусков одной реплики.**

   `src/sync_match_phase.py:479–494` независимо вызывает matcher для каждого фрагмента. Общий блок и номер фрагмента сохраняются после поиска как метаданные. Предыдущие выборы не участвуют в следующем сопоставлении.

   Если граница внутри предложения не обозначена, matcher ищет один непрерывный диапазон одного источника. Проверка с первой половиной фразы в источнике A и второй в B вернула только B: `needs_review`, 0.6087, «вернемся завтра». Объединённого совпадения для этого неразделённого запроса нет.

   Риски независимого поиска: повторное использование одного дубля несколькими частями, выбор несовместимых дублей, потеря контекста коротких фрагментов. Это архитектурные риски, а не измеренная частота ошибок на пользовательских проектах.

   Улучшение: сохранять несколько кандидатов на каждый фрагмент, затем выбирать лучшую комбинацию для блока. Учитывать покрытие текста, принадлежность спикеру, повторное использование материала, число склеек и совместимость соседних границ. Порядок в итоговом монтаже задаёт сценарий; хронологию исходника нельзя жёстко навязывать, поскольку редактор может намеренно переставлять части.

3. **Высокий приоритет: приблизительные таймкоды используются для точного монтажа.**

   Облачный путь распределяет слова равномерно по длительности реплики: `src/stage2/whisper_runner.py:322–328,361–377`, `src/stage2/sync_transcript.py:69–78`. Метаданные честно отмечают `timestamp_precision=interpolated`, однако условие автоматического совпадения в `sync_matcher.py:1582–1588` эту точность не проверяет.

   Дополнительно последняя реплика каждого облачного чанка растягивается до его границы с обнулением признака собственного конца (`src/stage2/cloud_asr.py:1763–1769`). Финальная сборка при отсутствии собственного конца использует следующую реплику или конец записи (`:1855–1879`). Это может распределить слова по паузе даже при наличии конца, ранее указанного моделью.

   Улучшение: разделить оценку совпадения текста и надёжность временных границ. После грубого поиска уточнять только выбранные интервалы по аудио. Вариант — forced alignment, то есть привязка распознанного текста к звуку; такой подход реализован в [WhisperX](https://github.com/m-bain/whisperX) и описан в [публикации авторов](https://arxiv.org/abs/2303.00747). Пригодность модели выравнивания для русского языка, оборудования и конкретных записей нужно проверить отдельно. Выравнивать следует фактически произнесённый текст каждого куска, а не принудительно весь отредактированный сценарий.

4. **Средний приоритет: нормализация границ опирается на неоднозначную пунктуацию.**

   `split_compound_quote()` делит по предложениям и многоточиям, а куски короче четырёх слов объединяет с соседними (`src/stage2/timeline_parser.py:52–92`).

   Воспроизведение: «Мы начали строить новый дом... Через год.» превращается в один фрагмент «Мы начали строить новый дом Через год.». Многоточие перестаёт быть границей. При этом обычные длинные предложения одной непрерывной реплики разделяются автоматически. Явные `СКЛ` в структурированных фрагментах Stage 1 — отдельный, уже поддержанный путь.

   После дополнительного разбиения стартовый и конечный таймкоды сохраняются только у первой части (`:164–172`); конечный таймкод не передаётся в запрос сопоставления (`src/api.py:1313–1324`, `src/sync_match_phase.py:479–487`). Остальные части теряют временной ориентир.

   Улучшение: хранить тип границы — явная склейка, таймкод, предполагаемая граница предложения или пауза. Явную склейку сохранять независимо от длины текста; короткий кусок искать с контекстом соседей. Для эвристических границ сравнивать цельное и составное совпадения. Общий временной диапазон блока хранить отдельно от границ его частей.

5. **Средний приоритет: память нормализации объединяет разные номерные метки.**

   `normalize_marker('Сергей 1')` и `normalize_marker('Сергей 2')` возвращают одинаковое значение `сергей`: `src/stage1/normalization_memory.py:51–70`. Это создаёт коллизию ключей обученных правил и подавлений. Для слитных форм «Сергей1» / «Сергей2» различие уже сохраняется.

   Исправление: снимать числовой суффикс только у известных служебных маркеров; идентификаторы людей сохранять. Старые неоднозначные правила памяти нужно выявить отдельно — исходное различие нельзя надёжно восстановить из одного нормализованного ключа.

   В проверенных путях нормализатора не найдено доказанной массовой потери текста или ошибки инвалидирования LLM-кэша. Различение дат и таймкодов уже реализовано и покрыто регрессиями. Полностью переписывать нормализацию оснований нет.

6. **Средний приоритет: проверка пропусков ASR не замечает начало чанка.**

   `find_coverage_holes()` проверяет интервалы начиная с первой распознанной реплики, но не от `part_start` до неё: `src/stage2/cloud_asr.py:1042–1080`.

   Воспроизведение: чанк 0–100 с, единственная реплика 80–90 с — результат `[]`. Для реплики 0–20 с в таком же чанке функция возвращает пропуск `(20, 100)`. Это не доказывает наличие речи в пропущенном начале, но показывает асимметрию проверки покрытия.

   Исправление: проверять начальный интервал и сопоставлять все предполагаемые пропуски с детектором активности речи. Повторно распознавать участки с речью; реальные тишину и паузы не отправлять в повторный платный проход.

7. **Средний приоритет: уверенность ASR теряется до сопоставления.**

   `_clean_words()` сохраняет только слово, начало и конец (`src/stage2/whisper_runner.py:153–176`). Путь faster-whisper также собирает только эти поля (`:265–273`). Между тем `WordTimestamp` и импорт транскрипта умеют хранить уверенность. Matcher оценивает текстовое сходство, не используя уверенность распознавания слова.

   Улучшение: сохранять доступные оценки ASR и происхождение таймкодов. Показывать отдельно сходство текста, полноту покрытия и качество временных границ. `confidence=1.0` сейчас не означает вероятность правильного монтажа 100%.

**Как ускорять без снижения качества**

Предлагаемые изменения требуют замеров; это не утверждение о текущем узком месте производительности.

- Два прохода: быстрый поиск по существующему индексу, затем точное выравнивание только выбранных и спорных интервалов.
- Повторное ASR — только для участков с подтверждённой речью и слабым распознаванием; кэшировать такие интервалы с учётом аудио, модели и настроек.
- Для большого числа фрагментов выбирать кандидатов по индексу редких слов/сочетаний, сохраняя резервный поиск. Сейчас фиксированные ограничения числа стартов ограничивают вычисления, но могут ограничивать полноту поиска.
- LLM оставлять для спорных кандидатов. Она не должна придумывать таймкоды или отсутствующие в распознавании слова. Текущий семантический обзор уже работает как дополнительный этап, а не полный перебор.
- Перед выбором модели или batch size измерить длительность ASR, поиска, уточнения границ, число повторов и стоимость на одинаковом наборе записей. Рекомендации «включить всё параллельно» без замера памяти и нагрузки здесь преждевременны.

**Предлагаемый порядок работ**

1. Добавить регрессии для большой паузы, одинаковых номерных меток, начального пропуска ASR и короткой части после склейки. Исправить эти локальные причины; разделить текстовую оценку и качество таймкодов.
2. Сделать явные границы фрагментов устойчивой частью нормализованного сценария. Сохранять оригинальный текст, связь с блоком и происхождение каждой границы.
3. Добавить совместный выбор кандидатов для составной реплики и уточнение границ по аудио. В интерфейсе показывать части, источники и причины ручной проверки.
4. Подобрать пороги на размеченной выборке реальных случаев: непрерывная речь, паузы, склейки внутри предложения, разные исходники, повторы дублей, числа, отрицания и смена спикера. Измерять полноту текста, долю ошибочных автоматических совпадений, ошибку начала/конца, время и стоимость. Только после этого выбирать более тяжёлые модели или менять поисковые лимиты.
