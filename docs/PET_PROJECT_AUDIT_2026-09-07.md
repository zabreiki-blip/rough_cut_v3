## Подтверждённые проблемы

### 1. P1 — пробный TTS загрязняет рабочий кэш тишиной

Код: `src/stage1/gemini_tts.py:696–708,734–744`.

`dry_run` сохраняет WAV-заглушку в тот же `assets/<uid>/<fingerprint>.wav`,
что настоящая озвучка. Следующая реальная генерация принимает этот WAV за
готовый кэш и пропускает синтез. У блоков с отдельным UID пробный запуск также
может перезаписать существующий настоящий asset тишиной. Позиционный `zk1.wav`
иногда остаётся прежним из-за проверки fingerprint — две копии расходятся.

Воспроизведение без API и настоящего синтеза:

```python
from pathlib import Path
from tempfile import TemporaryDirectory
from types import SimpleNamespace
from stage1 import gemini_tts as t

with TemporaryDirectory() as d:
    args = ([("zk1", "uid1", "Hello")], Path(d),
            "gemini", "voice", "female", 1.0,
            SimpleNamespace(gemini_tts_model="fake"))
    dry = t._plan_tts_items(*args, True, None)
    t._publish_local_item(dry[0], 1, [], [], None)
    print(t._plan_tts_items(*args, False, None)[0][-1])
```

Запуск с `PYTHONPATH=src .venv/bin/python` выводит `cache`, хотя реального
синтеза не было. Дополнительная проверка с ненулевыми PCM-данными подтвердила
перезапись asset нулевыми отсчётами.

**Исправление:** изолировать заглушки от production assets и их fingerprint;
dry-run не должен перезаписывать реальную озвучку. Добавить проверки переходов
«dry → real» и «real → dry → повторное использование» с отдельным UID.
Старый `AUDIT.md` помечает сохранность WAV при dry-run исправленной, но текущая
ветка работы с assets снова нарушает это свойство.

### 2. P1 — правки во время сохранения могут исчезнуть

Код: `src/static/stage1/normalization.js:241–245,486–517`;
`src/static/stage1/core.js:47–58`.

Нажать «Сохранить», затем продолжить править текст до ответа сервера.
Основные кнопки заблокированы, но поля блоков, удаление и перестановка доступны.
Ответ заменяет весь документ и сбрасывает `normalizationDirty`, уничтожая
сделанные во время запроса изменения без предупреждения.

**Проверено:** реальные `safely(saveNormalization)` и `updateBlockFromControl`
с задержанным ответом fetch. До ответа — новый текст и `dirty=true`; после —
старый сохранённый текст и `dirty=false`.

**Исправление:** для домашнего проекта достаточно блокировать редактор целиком
на время сохранения. Если нужна непрерывная работа — считать поколения локальных
правок и не заменять более свежий документ старым ответом.

### 3. P1 — экспорт CEP может связать звук A с секвенцией B

Код: `cep/js/main.js:991–1044,1200–1210,1255–1273`.

Запустить экспорт секвенции A, затем во время ожидания считать активную секвенцию
B в панели. При завершении экспорта регистрация заново читает текущие проект,
Source ID и `activeSource`, хотя WAV относится к A. Следом запускается
распознавание с неверной привязкой.

**Проверено:** реальный JS панели в Node VM с подставными host/XHR и четырьмя
проверками стабильности WAV отправил `source_id=B`, `sequence_id=B`,
`guide_audio=work/sync_audio/A.wav`. Это проверка логики панели, без запуска Adobe.

**Исправление:** при старте операции сохранить неизменяемый контекст: проект,
источник, секвенцию, путь, спикеров и backend. Использовать его до завершения
регистрации и запуска распознавания. Блокировка смены контекста дополнительно
сделает поведение понятнее.

### 4. P1 — удаление проекта конфликтует с фоновой обработкой

Код: `src/api_core_routes.py:339–350`;
`src/api_stage1_jobs.py:9–14`; `src/atomic_io.py:10–12`.

Удаление выполняет `shutil.rmtree` без блокировки переходов проекта и проверки
активных задач. Обработка может продолжить запись, создать каталоги заново и
оставить неполный проект вместо чистого удаления.

**Проверено:** во временном проекте при активной резервации нормализации
`DELETE /projects/audit` вернул 200 и удалил сценарий. Последующая штатная запись
статуса снова создала часть дерева проекта.

**Исправление:** взять существующий project lock и вернуть 409, пока выполняется
изменяющая проект задача. Для удобства и защиты от случайного удаления можно
заменить немедленное удаление переносом в корзину/архив.

### 5. P1 — новая папка просмотровок вытесняет старые источники

Код: `src/api_stage3_routes.py:355–365,326–333`;
для сравнения — `src/inbox_service.py:203–211`.

Если раньше файлы лежали в `media/reviews`, а потом появился хотя бы один файл
в `ЗАГРУЗИТЬ/Просмотровки`, Stage 3 сканирует только новую папку. Обзор inbox при
этом показывает обе. Регистрация заменяет список `review_media` и удаляет из него
источники старой папки. Исходные медиафайлы остаются, но связи сборки нарушаются.

**Проверено:** два настоящих секундных WAV во временном проекте. До добавления
нового файла источник — `media/reviews/old.wav`. После добавления `new.wav`
inbox показывает оба файла, а повторное сканирование/регистрация оставляет только
`ЗАГРУЗИТЬ/Просмотровки/new.wav`.

**Исправление:** сканировать обе поддерживаемые папки и объединять каталог до
обновления источников. Удалять старые регистрации только по результату полного
обзора. Тест должен проверять переход с legacy-папки на смешанное размещение.

### 6. P2 — текущая версия не проходит обязательный mypy

Код: `src/stage1/normalizer.py:1465–1466`;
`.github/workflows/ci.yml:47–48`.

Получен результат:

```text
src/stage1/normalizer.py:1466: error:
Item "None" of "Match[str] | None" has no attribute "end" [union-attr]
```

Шаблон `[.\s]*` допускает пустое совпадение, поэтому это не доказанное падение
во время исполнения: проблема в том, что типизатор не выводит гарантию совпадения.
Но `mypy` обязателен в CI, и эта проверка сейчас завершается с кодом 1.

**Исправление:** явно уточнить тип проверкой/assert перед `.end()` либо убрать
необходимость Optional-результата. Не отключать весь mypy ради одной строки.

### 7. P2 — пользовательская папка загрузки не исключена из Git

Код: `.gitignore:23–27`; `src/project_service.py:20–27`.

Исключены старые `input`, `media`, `work`, `speaker`, `versions`, но отсутствует
новая `projects/*/ЗАГРУЗИТЬ/`. Проверка `git check-ignore --no-index` на условных
путях сценария и видео не нашла исключений. Такие файлы можно случайно включить
в `git add .`, увеличив репозиторий и опубликовав личные материалы.

**Исправление:** исключить всю runtime-папку `projects/` либо добавить новую
папку отдельно. Тестовые материалы держать отдельно в fixtures. В текущем
индексе Git файлов из `projects/` не найдено — утечка этим аудитом не установлена.

## Оптимизации с понятной пользой

### 8. P2 — сузить контекст Docker-сборки

Код: `.dockerignore:1–13`; `docker-compose.yml:4`; `Dockerfile`.

Контекстом выбран корень репозитория, но `.dockerignore` не исключает `.venv`,
`node_modules`, большую часть `projects`, `data`, `artifacts` и `.env.bak.*`.
На этой машине `.venv` занимает 536 МБ, `node_modules` — 14 МБ, `projects` —
около 17 ГБ. Это размеры каталогов, а не измеренный объём передачи builder.
Реальная передача зависит от механизма сборки и используемых COPY.

**Исправление:** исключить runtime-данные и локальные окружения; разрешить только
нужные для сборки исходники, scripts и requirements. Это сокращает лишний обход
и доступность локальных данных в build context. Текущий Dockerfile копирует
выборочные пути — утверждать, что все эти данные попадают в образ, нельзя.

### 9. P2 — не вытеснять кэш ffprobe при смене папки

Код: `src/stage3/media_catalog.py:273–275,324–325`.

Кэш общий для `media_root`, но каждое сканирование заменяет его записями только
текущего каталога. Последовательность сканирований `a → a → b → a` на неизменных
файлах дала соответственно `1 → 0 → 1 → 1` новых вызовов probe. Проверено на
временных файлах с подставным `probe_media`.

**Исправление:** обновлять записи только внутри сканируемой области, сохраняя
остальные, либо разделить кэш по области сканирования. После объединения двух
папок в пункте 5 особенно важно не перезаписывать общий кэш двумя проходами.
Экономия проявится при повторных сканированиях; проценты ускорения без реальных
замеров не заявляются.

## Улучшения для удобства поддержки

1. **Добавить тесты переходов, обнаруженных в аудите.** При 724 зелёных тестах
   пропущены сочетания «проба → настоящая работа», «сохранение → новые правки»,
   «экспорт → смена источника», «обработка → удаление», «старые → смешанные папки».
   Именно такие проверки полезнее механического повышения общего coverage.
2. **Сделать простой резервный экспорт проекта.** История редакций внутри
   `projects/<name>/versions` не защищает от удаления всего проекта или поломки
   диска. Для домашнего использования достаточно копии проекта и базы памяти
   нормализации в отдельное место, с проверкой восстановления.
3. **Согласовать документацию с текущими проверками.** README:485–486 называет
   mypy/ESLint необязательными в CI, хотя оба обязательны. DEPENDENCY_POLICY:24
   указывает порог 75%, а `pyproject.toml` — 79%. README описывает lock-файл,
   тогда как политика говорит об отсутствии единого cross-platform lock.
   Нужна одна понятная инструкция: чем ставить зависимости и что запускать перед
   изменениями; исторические сведения обозначить явно.
4. **Упрощать большие модули при следующем изменении их функций.** Например,
   `normalizer.py` — 2177 строк, `cloud_asr.py` — 1531, `cep/host.jsx` — 3493.
   API-модули передают весь `api` через `sys.modules[__name__]` как набор зависимостей.
   Постепенно выделять узкие функции/контексты проще, чем поддерживать новые
   обходы глобального состояния. Массовая перепись ради числа строк не нужна.
5. **Измерить один типичный сквозной проект.** Отдельно записать длительность
   нормализации, TTS, ASR, сопоставления и сборки XML, попадания в кэш и память
   Whisper. Решения об увеличении параллелизма принимать по этим данным.
   Существующие кэши, ограниченные пулы и тёплый Whisper уже дают базовую
   оптимизацию; добавление нескольких gunicorn workers нарушит текущую модель
   внутрипроцессных блокировок.

## Практический порядок работ

Сначала исправить TTS-кэш и потерю текста, затем привязку CEP, смешанные папки
и удаление занятого проекта. Каждое исправление закрепить воспроизведённым
сценарием. Отдельной небольшой уборкой восстановить mypy, поправить исключения
Git/Docker и документацию. После этого исправить кэш сканирования и провести
один полный пилот в Premiere по существующему `docs/E2E_PILOT_CHECKLIST.md`.

Для одного пользователя Flask, файловые артефакты и один процесс остаются
разумной основой. Очередь с Redis/Celery, отдельные сервисы и перенос всего
хранилища в СУБД найденные проблемы сами по себе не решат.
