## Подтверждённые ошибки

### P1 — части меток ЗК попадают в текст озвучки: 52 из 68 блоков

Исходник содержит составные номера вроде `ЗК0.1` и `ЗК1.10`.
В [normalizer.py](../src/stage1/normalizer.py), `_split_label`, строки 1594–1612,
регулярное выражение распознаёт только первую числовую часть; точка съедается
как разделитель, а оставшаяся часть номера становится началом реплики.

| Исходная строка | Фактический normalized/TTS text |
| --- | --- |
| `ЗК0.1 25 марта 2025 года.` | `1 25 марта 2025 года.` |
| `ЗК1.10 Продолжение истории.` | `10 Продолжение истории.` |
| `ЗК1: 25 марта 2025 года.` | `25 марта 2025 года.` — корректно |
| `ЗК 25 марта 2025 года.` | `25 марта 2025 года.` — корректно |

В реальном проекте первый пример есть в блоке №2, UID `block-2-6ec82832`,
prepared ID `zk1`: [scenario_prepared.json](../projects/UIP_ATOM_001/work/scenario_prepared.json),
строки 11–14. Второй реальный пример — `zk3`, начало `2 21 июня 2025 года…`.

Все затронутые prepared IDs: **zk1, zk3–zk10, zk17–zk26, zk32–zk59, zk64–zk68**.
Их `normalized_text` и `text_for_tts` содержат остаток номера. Проекция
`_prepared_projection` (normalizer.py:2516–2543) переносит его в prepared JSON.
TTS-задача для этой редакции уже завершена, WAV существуют. Подтверждена ошибка
текста, переданного в озвучку; прослушивание и проверка фактически произнесённых
слов в этом аудите не выполнялись.

Воспроизведено как прямым вызовом `_split_label`, так и полной нормализацией
временного TXT с `use_llm=False`. Существующие тесты numbered markers проходят,
но составные номера с точкой не покрывают.

Исправление: разбирать составной номер целиком, не удаляя даты/числа из самой
реплики; добавить регрессии на обе формы и контрольные строки. Затем обновить
только затронутые блоки с сохранением UID и ручных правок, переподтвердить
проекцию, проверить и при необходимости пересоздать соответствующую озвучку.

### P2 — имя медиафайла включено в искомую реплику СНХ

Блок №5, UID `block-10-47fe0295`, Виктор Литовкин: первый canonical fragment
заканчивается `…Дональд Трамп. ZOOM0007_Tr1 (1).WAV`.
См. [scenario_normalized.json](../projects/UIP_ATOM_001/work/scenario_normalized.json):163.

Начальный credit корректно разбирается `_parse_snh_dash_credit`, но повторное
имя файла перед таймкодом второй реплики остаётся хвостом первой.
`_extract_sync_fragments` (normalizer.py:1907–1960) режет текст по таймкодам,
не отделяя этот повторный media credit. `_sync_alignment_units`
([api.py](../src/api.py):1359–1382) использует готовый fragment text напрямую.
`SyncMatcher.match` ([sync_matcher.py](../src/stage2/sync_matcher.py):1503)
сохраняет лишние токены `zoom0007`, `tr1`, `1`, `wav` в поисковом запросе.

Подтверждено загрязнение запроса служебными данными. Ухудшение конкретного
совпадения или неверный монтаж этого фрагмента ещё не доказаны: текущая задача
сопоставления не завершена. Повторное имя файла следует хранить как метаданные
источника, исключив его из spoken fragment.

### P2 — интерфейс сборки скрывает предупреждения backend

`_stage2_build` возвращает `warnings`, в том числе отсутствие WAV, пропущенные
устаревшие sync matches и ошибки создания карточек
([api_stage2_routes.py](../src/api_stage2_routes.py):939–950).
`doBuildTimeline` в [tts.js](../src/static/stage1/tts.js):467–487 использует только
число ЗК, число СНХ и длительность, затем включает экспорт. `warnings`,
`matched`, `review`, `unmatched` не выводятся.

В Node VM выполнено тело настоящей `doBuildTimeline` с подменённым ответом API,
содержащим предупреждения об отсутствующем WAV и устаревших matches. В журнале
остались только сообщения о начале и успешной сборке, `timelineReady=true`,
кнопка экспорта включена. Это воспроизведение UI-дефекта на тестовом ответе;
в текущем UIP_ATOM все 68 WAV присутствуют.

Исправление: показывать предупреждения и результат сопоставления рядом с
результатом сборки; явно отличать готовую сборку от черновика с заглушками.

### Два needs_review: ошибочные времена Попова, блок №50

UID `block-34-40304696`, два фрагмента. Найденный текст почти точно совпадает,
но retimed speech ranges равны **235.27–235.69** и **235.79–236.19 с**:
21 и 20 слов помещены в 0.42 и 0.40 секунды. В retimed index слова имеют
длительность по 20 мс. Локальная расшифровка этого участка содержит другой
вопрос интервьюера. Нужные реплики в local index находятся около
**268.08–281.96** и **286.35–294.43 с**.

В сохранённых alternatives уже есть соответствующие диапазоны с запасом:
**04:26.080–04:43.460** и **04:44.350–04:55.930**. Это кандидаты для
прослушивания, не автоматическая замена текущих границ.

`_timing_gate_flags` (sync_matcher.py:404–418) доверяет метке `retimed` целого
индекса. Проверка gaps (1633–1643) отлавливает длинные паузы/слова, но не
схлопывание длинной реплики до долей секунды. Глобальные quality gates
`word_retiming.py:388` не подтверждают достоверность каждого отдельного участка.
`_make_monotone` (548–561) устанавливает минимальную длину слова 20 мс.
Точная ошибочная пара anchors не установлена: виды выравнивания каждого слова
не сохранены. Подтверждена ошибка итоговых времён относительно local index.

  `block-8-31a20c26::fragment:2` по-прежнему требует проверки хвоста.
- В `full_timeline.json` 174 сегмента: 68 ЗК, 85 СНХ, 6 ведущего, 15 технических.
  Установка новой версии кода сама по себе их не исправляет.

**Действие:** адресно исправить 52 блока и загрязнённый sync fragment с
сохранением UID и ручных правок, переподтвердить нормализацию, пересоздать
затронутую озвучку и проверить сопоставление с уже существующими local indexes.
После проверки спорных диапазонов пересобрать таймлайн и XML. Массовую замену
подтверждённых границ без прослушивания не включать в автоматическую миграцию.

Критерий закрытия: prepared/TTS соответствуют исправленному тексту;
перечисленные проблемные совпадения проверены, а новая сборка принадлежит
актуальной редакции. До этого прежнюю озвучку и XML нельзя считать исправленными
только на основании обновления исходников.

### U2 · P2 — подтверждение нормализации может незаметно удалить новые правки

**Воспроизведено на настоящих JS-функциях с задержанным mock-ответом API.**

`setBusy(true)` блокирует кнопки действий, но оставляет поля блоков доступными
для ввода: [core.js](../src/static/stage1/core.js):47–59.
`confirmNormalization` после ответа безусловно заменяет документ, выставляет
`confirmed` и очищает `normalizationDirty`:
[normalization.js](../src/static/stage1/normalization.js):392–409.

Воспроизведение: начать подтверждение текста `original`; до ответа POST изменить
текст для TTS на `new edit during confirm`; вернуть успешный ответ с исходным
снимком. Вызов выполнялся через настоящий `safely`, как при клике в UI.

```text
После ответа: text="original", dirty=false, eligible=true, revision=6
```

Поздняя правка исчезает, предупреждение о несохранённых изменениях тоже.
Обработчики ввода продолжают работать во время запроса; ограничение кнопок
не защищает этот сценарий.

**Исправление:** либо блокировать редактирование на весь цикл подтверждения,
включая preview, либо проверять поколение правок перед применением ответа и
сохранять более новый локальный текст как неподтверждённый черновик.
Регрессия должна проверять ввод во время preview и во время final POST,
сохранность текста и `dirty`/`eligible` после ответа.

### U3 · P2 — ввод во время сохранения оставляет клиент на старой revision

**Воспроизведено отдельно от потери правок при подтверждении.**

В [normalization.js](../src/static/stage1/normalization.js):322–328 уже есть
защита от перезаписи нового текста: если изменился `normalizationEditGeneration`,
ответ PUT отбрасывается. Вместе с текстом теряется и новая серверная revision.
Backend увеличивает её при сохранении и проверяет при следующем запросе:
[normalizer.py](../src/stage1/normalizer.py):725–732, 766–767.

```text
PUT отправлен с revision=5; во время ожидания внесена новая правка.
Ответ сервера: revision=6.
Состояние клиента: revision=5, dirty=true, новый текст сохранён в памяти.
Следующий PUT: revision=5 → конфликт "Expected revision 5, current revision is 6".
```

**Исправление:** принять revision успешного сохранения, сохранив более новые
локальные правки и `dirty=true`; учитывать возможные серверные преобразования
документа при слиянии. Альтернатива — блокировка ввода на время сохранения.
Критерий закрытия: два последовательных сохранения с вводом между отправкой
и ответом первого PUT завершаются успешно и сохраняют последний текст.

### U4 · P2 — обновление статуса не обновляет готовность таймлайна в UI

**Воспроизведено; серверная проверка актуальности остаётся работающей.**

`appState.timelineReady` инициализируется из начального HTML и устанавливается
в `true` после локальной сборки. `applyStatus` игнорирует присланный
`timeline_ready`: [normalization.js](../src/static/stage1/normalization.js):527–565;
[state.js](../src/static/stage1/state.js):199;
[tts.js](../src/static/stage1/tts.js):514.

Сценарий: таймлайн был готов, затем другой клиент изменил matches; обновление
статуса возвращает `timeline_ready=false`. После `applyStatus` получено:

```text
server timeline_ready=false; UI timelineReady=true; exportDisabled=false
```

Обратный переход тоже пропущен: сборка другим клиентом не включит экспорт
после обычного обновления статуса. Требуется полная перезагрузка или новая
локальная сборка. Сервер проверяет редакцию и fingerprint matches и отвергает
устаревший экспорт с 409: [api_stage3_routes.py](../src/api_stage3_routes.py):923–931.
Это рассогласование UI, а не доказательство выдачи устаревшего XML.

**Исправление:** при наличии булевого `timeline_ready` обновлять поле состояния
перед `updateActionAvailability`. Проверить оба перехода и состояние кнопки
при параллельно работающей Stage 3 задаче.

### Оптимизация и улучшения

Следующие пункты — предложения, а не дополнительные доказанные аварии.

1. **Отслеживать необходимость пересоздания артефактов после исправлений.**
   Показывать рядом со статусом редакции отдельный признак проверки результатов
   текущей версией нормализатора/сопоставления. Сохранять версию алгоритма
   в происхождении производных артефактов. Fingerprint v5 уже решает часть
   задачи для повторного matching; старые prepared/TTS этим не обновляются.
   Предусмотреть просмотр diff и выборочное пересоздание затронутых блоков.
2. **Добавить проверки реального сценария редактирования в браузере.**
   18 текущих Stage 1 JS-тестов используют минимальный DOM; они не проверяют
   ввод в поле во время запроса, восстановление после конфликта и обновление
   готовности между вкладками. Покрыть U2–U4 задержанными ответами; дополнить
   одним браузерным сценарием «правка → сохранение → подтверждение → сборка».
3. **Включить веб-модули в статическую проверку JavaScript.**
   Сейчас CI проверяет ESLint только для `cep` и `tests/cep_behavior_test.cjs`
   (ci.yml:114–115). Пробный запуск для `src/static` с `sourceType=module`,
   `ecmaVersion=2022` нашёл одно замечание: `tts.js:148`,
   `no-constant-condition` на `while (true)`. Цикл имеет выходы; замечание
   само по себе не доказывает зависание. Настроить правила для осознанных
   polling-циклов и сделать проверку веб-модулей обязательной.
4. **Сократить полное перестроение редактора на больших сценариях.**
   `renderNormalization` удаляет и заново строит все карточки; для каждой
   повторно фильтрует весь список блоков при формировании выбора объединённой
   озвучки: normalization.js:151–205. При 139 блоках это 19 321 проверка
   кандидатов только для таких селектов. `focusIssue` также запускает полный
   render (:83–98). Предварительно вычислять список кандидатов, обновлять
   только изменённую карточку и рассмотреть ленивое заполнение селектов.
   Выигрыш по времени ещё не измерен: сначала снять профиль на 139 и 1000
   блоках, включая длительность отрисовки и сохранение фокуса/позиции ввода.
5. **Не ускорять backend простым увеличением числа Gunicorn workers.**
   Project locks, реестры задач и дедупликация reconciliation находятся в
   памяти процесса: [api.py](../src/api.py):256–280, 411–459;
   [versioning.py](../src/stage4/versioning.py):66–80. Штатный deployment
   использует один worker. Для нескольких процессов сначала нужны общие
   блокировки/атомарное резервирование задач; это условный риск масштабирования,
   уже частично учтённый в D31 [TECH_DEBT.md](TECH_DEBT.md).
6. **Проверить ASR-функции совместно на фиксированной короткой записи.**
   Общие фикстуры [conftest.py](../tests/conftest.py):31–65 отключают local repair,
   hole VAD и retiming; специализированные тесты включают их с подменами.
   Нужен отдельный интеграционный прогон с эталонными фразами и границами,
   включая fallback, повторный запуск из кэша и сохранность ручных подтверждений.
   Перед оптимизацией измерить время ASR, retiming, matching и число обращений
   к провайдеру по отдельности. Зелёные unit-тесты не заменяют эту проверку.
