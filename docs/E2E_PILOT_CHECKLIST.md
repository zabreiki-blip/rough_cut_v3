# E2E Pilot Checklist — сквозной пилот в реальном Premiere Pro

Сквозной прогон с conform в реальном Premiere Pro пока не подтверждён
сохранённым отчётом. Сборка BRIK в Stage 2/3 и экспорт XML не заменяют эту
проверку. Документ — пошаговый чек-лист для ручного прогона на Mac; версию
Premiere и модель чипа следует записать перед стартом.

## 1. Назначение и гипотезы

Мы не проверяем «работает всё» — мы целенаправленно проверяем пять
конкретных гипотез:

1. Реальный `.docx` с ЗК и синхронами вперемешку нормализуется без
   потери и без переклассификации блоков.
2. TTS-озвучка (`TTS_PROVIDER=macos`, `say`) даёт валидные WAV для
   каждого блока ЗК.
3. Три синхрона, разнесённые по одной просмотровке 3-5 минут с
   посторонней речью между ними, находятся автоматическим
   сопоставлением (Whisper + fuzzy match), включая реплику с
   оговоркой.
4. CEP-панель в реальном Premiere Pro регистрирует sync-секвенцию,
   экспортирует guide WAV, запускает распознавание и корректно
   расставляет маркеры `RC_SYNC_*` при conform — включая повторный
   (идемпотентный) conform после изменённого недавно механизма
   индексации маркеров по имени (коммит `13c9e9a`).
5. Ручная правка маркера в Premiere между двумя проходами conform не
   приводит к рассинхрону — приложение видит актуальное состояние
   секвенции, а не устаревший кэш.

Каждый шаг ниже проверяет одну или несколько из этих гипотез, а не
факт «кнопка нажалась».

## 2. Предусловия

### 2.1 Материал пилота

- Сценарий `.docx`, 1 страница, 6 блоков в порядке: ЗК, синхрон, ЗК,
  синхрон, синхрон, ЗК (3 блока ЗК + 3 синхрона).
- Одна просмотровка (видео с записанным звуком) длительностью
  3-5 минут, где эти 3 реплики синхронов разнесены по таймлайну и
  между ними звучит посторонняя речь (не связанная со сценарием).
- Одна из трёх реплик синхрона в просмотровке произнесена с
  оговоркой/запинкой относительно текста в сценарии — это тестирует
  fuzzy-матчинг, а не точное совпадение.

### 2.2 Запуск backend

```bash
export PYTHONPATH=src
.venv/bin/flask --app api run --host 127.0.0.1 --port 8000
```

Перед стартом убедиться, что в `.env` заданы:
- `ROUGH_CUT_API_TOKEN` (пароль для Basic Auth в браузере);
- `TTS_PROVIDER=macos`.

Для альтернативного запуска можно использовать `scripts/run-local` (gunicorn,
один worker, четыре thread, timeout 3600):

```bash
PYTHONPATH=src scripts/run-local
```

В отчёте указать, какой из двух вариантов запуска использовался.

Проверить `/health` (без токена):

```bash
curl -s http://127.0.0.1:8000/health
```

Ожидаемый результат: HTTP 200, тело без ошибки.

### 2.3 Установка CEP-панели

```bash
scripts/install-cep-macos
```

По инструкции `cep/README.md`:
- скрипт создаёт symlink `cep/` в
  `~/Library/Application Support/Adobe/CEP/extensions/rough-cut-v3-sync`
  и включает `PlayerDebugMode` для CSXS 11/12;
- перезапустить Premiere Pro;
- открыть `Window → Extensions → Rough Cut — Синхронизация`.

В панели при первом запуске указать: проект, backend URL
(`http://127.0.0.1:8000`), Bearer token (значение
`ROUGH_CUT_API_TOKEN`) и общий каталог `projects` этой машины (нужен
для пути `<projects>/<project>/work/sync_audio/<source_id>.wav`).

### 2.4 Запись в отчёт до старта

- версия Premiere Pro;
- версия macOS;
- модель Mac (уточнить чип: Intel или Apple Silicon);
- git-коммит репозитория (`git rev-parse HEAD`).

## 3. Шаги по этапам

Открыть в браузере `http://127.0.0.1:8000/`, создать проект (кнопка
на стартовой странице, `GET|POST /projects`), перейти в
`GET /project/<project>`. Файлы для загрузки положить заранее в:

```text
projects/<project>/ЗАГРУЗИТЬ/Сценарии/  — .docx сценарий
projects/<project>/ЗАГРУЗИТЬ/Просмотровки/ — видео/wav просмотровки
```

### Этап A. Нормализация (вкладка «Нормализация»)

1. **Шаг:** указать путь к `.docx` в поле «Исходный сценарий»,
   нажать «Нормализовать» (`btn_normalize` →
   `POST /stage1/normalization-jobs/start`, затем опрос
   `GET /stage1/normalization-jobs/<job_id>`).
   **Ожидаемо:** появляются 6 блоков в правильном порядке (ЗК,
   синхрон, ЗК, синхрон, синхрон, ЗК), счётчики «Закадр»/«Синхрон»
   равны 3/3, «Требует проверки» = 0.
   **Артефакт:** `projects/<project>/work/scenario_prepared.json` и
   canonical `projects/<project>/work/scenario_normalized.json`.
   **В отчёт:** число блоков, распределение по типам, были ли
   блоки в «Требует проверки».

2. **Шаг:** визуально сверить текст каждого блока с оригиналом
   `.docx` (переносы строк внутри абзаца сохраняются в одном блоке).
   **Ожидаемо:** текст не обрезан и не склеен между блоками.
   **В отчёт:** расхождения, если есть.

3. **Шаг:** нажать «Подтвердить сценарий» (`btn_confirm_normalization`
   → `POST /stage1/normalization/confirm`, при наличии ручных
   исправлений — сначала диалог «Что запомнить из исправлений?»).
   **Ожидаемо:** статус сценария переходит в `confirmed`, разблокируются
   вкладки «Озвучка» и «Сборка» (пропадают иконки замка).
   **Артефакт:** `scenario_normalized.json` со `status: confirmed`.
   **В отчёт:** потребовалось ли ручное исправление типа блока.

### Этап B. Озвучка (вкладка «Озвучка»)

4. **Шаг:** убедиться, что `TTS Provider = macOS (say)`, пол голоса
   на выбор, нажать «TTS» (`btn_tts` →
   `POST /stage1/tts-jobs/start`, live-прогресс через
   `GET /stage1/tts-jobs/<job_id>`).
   **Ожидаемо:** 3 WAV-файла созданы (по числу блоков ЗК), «Live TTS»
   доходит до 3/3 без ошибок в `live_error`.
   **Артефакт:** `projects/<project>/speaker/zk1.wav`, `zk2.wav`,
   `zk3.wav`.
   **В отчёт:** время выполнения, были ли повторы (`live_retries`).

5. **Шаг:** нажать «Validate» (`btn_validate` →
   `POST /stage1/validate`).
   **Ожидаемо:** предупреждений по длительности/тишине нет (или
   ожидаемые, если реплика короткая).
   **Артефакт:** `projects/<project>/speaker/manifest.json`.
   **В отчёт:** содержимое warnings, если есть.

### Этап B′. Платный smoke-тест OpenRouter MAI-Voice-2

Перед шагом проверить, что в `.env` задан `OPENROUTER_API_KEY`; значение ключа
не включать в отчёт. Этот шаг выполняется только для одной короткой фразы и
подтверждает миграцию на `/audio/speech`.

5′. **Шаг:** во вкладке «Озвучка» выбрать провайдер `openrouter`, выключить
`dry_run` и озвучить одну короткую фразу через `POST /stage1/tts-phrase`.
Можно использовать параметры `voice_name`, `speed` и `speaker_dir` из UI.
**Ожидаемо:** ответ успешен, WAV не тихий (PCM содержит ненулевые отсчёты),
mono, примерно 24 кГц, длительность соответствует фразе; в логе нет ошибок
SSE/парсинга.
**В отчёт:** время ответа, параметры WAV, фактические модель и голос. При
провале сохранить HTTP-код и тело ответа: это отдельная находка по миграции
OpenRouter TTS.

### Этап C. Регистрация sync-секвенции в Premiere (CEP-панель)

Подготовка в Premiere: импортировать просмотровку, смонтировать/
синхронизировать 3-минутную секвенцию с 3 синхронами и посторонней
речью (или использовать уже готовую sync-секвенцию, если она есть в
проекте). Сделать эту секвенцию активной.

6. **Шаг:** в CEP-панели нажать «Использовать активную» (host-команда
   `rcStage2_inspectActiveSequence`/`rcStage2_resolveSequence`).
   **Ожидаемо:** панель показывает имя и ID секвенции, badge host
   зелёный.
   **В отчёт:** имя секвенции, sequence ID.

7. **Шаг:** указать спикера/спикеров и ASCII `source_id`
   (`^[A-Za-z0-9_-]{1,96}$`), нажать «Экспортировать звук и запустить
   распознавание» (`rcStage2_exportActiveSequenceAudio` →
   `POST /stage2/sync-sources` → polling WAV → `POST /stage2/sync-jobs/start`).
   **Ожидаемо:** WAV экспортирован через Adobe Media Encoder, панель
   показывает переход к фоновому распознаванию.
   **Артефакт:** `projects/<project>/work/sync_audio/<source_id>.wav`,
   `projects/<project>/work/sync_sources.json`.
   **В отчёт:** длительность экспорта WAV, ошибки Encoder job (если
   были).

### Этап D. Распознавание и сопоставление (вкладка «Сборка», раздел
«Автоматическое сопоставление СНХ»)

8. **Шаг:** выбрать движок «Локально» и модель Whisper (`small` для
   первого прохода), нажать «Найти СНХ автоматически»
   (`btn_sync_align` → `POST /stage2/sync-jobs/start`, опрос
   `GET /stage2/sync-jobs/status`).
   **Ожидаемо:** прогресс-бар доходит до конца, счётчики «Найдено» /
   «Проверить» / «Не найдено» заполняются (ожидаем 3 совпадения из
   3 синхронов сценария).
   **Артефакт:** `projects/<project>/work/transcripts/<source_id>.words.json`,
   `projects/<project>/work/sync_matches.json`.
   **В отчёт:** время распознавания (`sync_metric_wall_time`),
   движок (`sync_metric_backend`).

9. **Шаг (особая проверка — оговорка):** найти в списке результатов
   реплику с оговоркой. Посмотреть её `confidence`/статус в блоке
   «Требуют проверки» (`sync_review_list`) или, если совпадение
   попало в «Найдено» — открыть `sync_matches.json` и найти это
   `block_uid`.
   **Ожидаемо по логике matcher (`src/stage2/sync_matcher.py`):**
   `confidence >= 0.78` допускает `auto_matched` только при отсутствии
   неоднозначности, смысловых флагов, большой паузы, глобального fallback
   и ненадёжных таймкодов. Интерполированное время без локального уточнения
   даёт `needs_review` даже при точном совпадении текста. Кандидаты ниже
   порога ручной проверки (`0.50`) получают `not_found`.
   **В отчёт:** фактический `confidence`/score, статус, `timing_flags` и
   `timestamp_precision` из метаданных, потребовалось
   ли ручное подтверждение через «Прослушайте диапазон...», какая
   реплика (1/2/3) оказалась с оговоркой.

10. **Шаг:** для записей со статусом `needs_review` (жёлтые)
    прослушать диапазон, подтвердить или выбрать альтернативу
    (`PATCH /stage2/sync-matches/<block_uid>`).
    Если подтверждённый ранее фрагмент помечен `retime_pending_review`,
    он снова появляется в очереди проверки после уточнения таймкодов:
    проверить границы и подтвердить повторно перед сборкой.
    **Ожидаемо:** после подтверждения статус переходит в `confirmed`,
    счётчик «Подтверждено» растёт.
    **В отчёт:** сколько записей потребовали ручного подтверждения.

### Этап E. Сборка таймлайна и conform в Premiere

11. **Шаг:** нажать «Build Timeline» (`btn_build_timeline` →
    `POST /stage2/build`).
    **Ожидаемо:** таймлайн собран, статистика `ts_zk`/`ts_snh`/`ts_dur`
    заполнена (3 ЗК, 3 синхрона).
    **Артефакт:** `projects/<project>/work/full_timeline.json`.

12. **Шаг:** нажать «Export XML» (`btn_export_xml` →
    `GET /stage2/export/xml`), импортировать XML в Premiere (готовая
    Rough Cut секвенция с плейсхолдерами под синхроны).
    **Ожидаемо:** секвенция открывается без ошибок импорта.

13. **Шаг:** сделать импортированную Rough Cut секвенцию активной в
    Premiere, в CEP-панели нажать «Применить подтверждённые СНХ»
    (batch conform, host-команда `rcStage2_conformSequenceRanges`).
    **Ожидаемо:** все 3 плейсхолдера синхронов заменены реальными
    диапазонами из sync-секвенции; на каждой вставке появляется
    маркер `RC_SYNC <...>` (см. п. 4.1 ниже); панель показывает отчёт
    `requested/completed/errors` без ошибок.
    **В отчёт:** содержимое отчёта, число созданных маркеров, их
    имена и позиции (сверить на глаз с таймлайном Premiere).

### Этап F. Финальная проверка собранного таймлайна

После шага 13 оставить активной собранную и conform-нутую Rough Cut секвенцию.

F1. **Шаг:** нажать «Проверить собранный таймлайн». Host экспортирует WAV через
`exportFinalReview`, затем панель вызывает `POST /stage2/final-review/estimate`
и показывает стоимость/лимит до подтверждения. Подтвердить запуск:
`POST /stage2/final-review/start` передаёт точную строку `confirmed_estimate_usd`.
**Ожидаемо:** статус «Распознаю и сверяю…». Артефакты:
`work/final_review.wav` и `final_review_job_status.json`.
**В отчёт:** время старта/экспорта, `estimated_cost_usd`, `cost_limit_usd`,
`enforced`. Изменить оценку между estimate и Start: HTTP 409 требует нового
подтверждения. При отключённом лимите/неизвестной оценке проверить явное
предупреждение, что сумма не ограничивает оплату.

F2. **Шаг:** дождаться завершения при опросе примерно каждые 3 секунды.
**Ожидаемо:** в логе панели «Финальная проверка завершена», кнопка «Создать
исправленную итерацию» активна. Артефакт:
`work/final_review_report.json`.
**В отчёт:** `expected_segments`, `findings`, `missing`, `truncated`,
`automatic_corrections`; для корректного монтажа ожидается 0 error-findings.

F3. **Шаг:** нажать «Создать исправленную итерацию». Панель вызывает
`POST .../apply`, клонирует секвенцию с именем « · RC iteration N» и применяет
corrections в клоне.
**Ожидаемо:** исходная секвенция не изменена; при corrections=0 создана
черновая копия без правок; маркеры `RC_SYNC_*` сохранены.
**В отчёт:** имя клона, число corrections и изменения в клоне.

F4. **Особые проверки:**

- Перезагрузить панель во время проверки и после завершения: latest должен
  восстановить job ID/статус/отчёт. Apply доступен после подтверждения совпадения
  `sequenceId`; при другой активной секвенции заблокирован. Смена проекта не
  должна показывать результат прежнего проекта. После рестарта сервера активная
  задача становится `interrupted`, Apply недоступен.
- Отключить API во время опроса: проверить задержки 3, 6, 12, 24, 30 секунд,
  затем Retry. Вернуть API и нажать Retry: продолжается тот же job ID, новый
  платный Start не выполняется. Скрыть/открыть панель: опрос возобновляется один
  раз, старые ответы не меняют текущий экран.
- Нажать Cancel во время работы и ожидания ASR: `cancelling` переходит в
  `cancelled`, проект освобождается. Проверить пояснение о возможной оплате уже
  отправленного запроса и поля `cost_usd`, `reserved_cost_usd`, `cost_pending`.
  При неизвестной цене панель показывает pending/резерв, в том числе при
  нулевой оценке. Запустить следующую задачу, перезапустить сервер и проверить
  сохранённый `reserved_cost_usd` pending-события журнала отдельно от
  подтверждённой суммы. Истечение
  `FINAL_REVIEW_TIMEOUT_SECONDS` даёт `failed` с timeout.
- Повторить сетевой запрос Apply с тем же `request_id`: сервер возвращает ту же
  итерацию. После успешного Apply открыть исходную секвенцию, вернуться в
  панель для обновления статуса: новый явный Apply использует новый `request_id`
  и создаёт вторую итерацию, сохраняя первую. Проверить последовательные имена клонов и отсутствие
  повторных правок исходной секвенции.
- При усечённом snh/host проверить захват расширенным диапазоном начала/конца
  реплики.

## 4. Точки особого внимания

### 4.1 Conform нескольких синхронов и индекс маркеров по имени

Коммит `13c9e9a` («Index sequence markers by name during conform»)
заменил полный обход коллекции маркеров на индекс по имени
(`exactMarkersNamed` в `cep/host.jsx`) для ускорения batch conform.
Индекс инвалидируется в 8 точках мутации маркеров и дополнительно
сбрасывается на входе каждой публичной host-операции
(`invalidateMarkerIndexCache`). Это первый реальный (не юнит-тестовый)
прогон этого механизма — проверить прицельно:

- **Создание маркеров.** После batch conform в п. 13 в секвенции
  должно быть ровно 3 маркера с префиксом `RC_SYNC ` (без дублей, без
  «призрачных» маркеров от промежуточных re-anchor попыток —
  временные маркеры называются `RC_SYNC_REANCHOR_TMP` и не должны
  оставаться в финальном состоянии).
- **Тайминги маркеров.** Позиция каждого маркера должна совпадать с
  началом вставленного диапазона синхрона на таймлайне (проверить на
  глаз по TC в Premiere).
- **Идемпотентность повторного conform.** Повторно нажать «Применить
  подтверждённые СНХ» без изменений в проекте.
  **Ожидаемо:** маркеры не дублируются (по одному на элемент), панель
  сообщает, что элементы уже конформлены/пропущены, либо повторно
  проверяет существующий маркер без создания нового. Зафиксировать в
  отчёте фактическое число маркеров до и после повторного прохода.

### 4.2 Реплика с оговоркой (fuzzy-матчинг)

Записать явно:
- к какому блоку сценария она относится (zk/snh N);
- итоговый `confidence`/score из `sync_matches.json`;
- итоговый `status` (`auto_matched`/`needs_review`/`not_found`);
- потребовалось ли ручное подтверждение в разделе «Требуют
  проверки»;
- совпал ли выбранный диапазон `source in/out` с реальным
  расположением реплики в просмотровке (прослушать).

### 4.3 Ручная правка маркера между двумя conform-проходами

Тест на актуальность состояния (не устаревший кэш):

1. После первого conform (п. 13) вручную сдвинуть или переименовать
   один из маркеров `RC_SYNC ...` прямо в Premiere (или удалить его).
2. Не перезапуская Premiere и не закрывая CEP-панель, снова нажать
   «Применить подтверждённые СНХ».
   **Ожидаемо:** приложение видит актуальное (изменённое вручную)
   состояние секвенции — не создаёт дубликат поверх старого
   индекса и не игнорирует ручную правку. Это прямая проверка
   поведения «индекс сбрасывается на входе каждой публичной
   операции» из коммита `13c9e9a`.
   **В отчёт:** что именно было изменено вручную, что показал второй
   conform-проход (создан новый маркер / переиспользован старый /
   ошибка), совпадает ли итоговое состояние с ожиданием.

## 6. Что собрать при сбое

### 6.1 Логи backend

Приложение логирует через `src/logging_config.py` в `stderr`
(отдельный файл логов backend по умолчанию не создаётся —
`LOG_LEVEL` управляет уровнем, вывод нужно перенаправить вручную,
например `... 2>&1 | tee /tmp/rough_cut_backend.log`, если лог не
сохранялся заранее). Если backend запускался через
`scripts/run-local` (gunicorn) — также перенаправить stdout/stderr в
файл при следующем прогоне.

Каталог `logs/` в репозитории используется только для macOS TTS
коннектора (`scripts/run-macos-connector`), если он применялся:
- `logs/macos-connector.log`
- `logs/macos-connector.error.log`

### 6.2 JSON-артефакты проекта

Приложить целиком (без изменений) из `projects/<project>/work/`:
- `scenario_normalized.json`
- `sync_sources.json`
- `sync_matches.json`
- `full_timeline.json`
- статус последней sync-job: ответ
  `GET /stage2/sync-jobs/status?project=<project>`
- статус последней TTS-job: ответ
  `GET /stage1/tts-jobs/status?project=<project>`

### 6.3 Вывод CEP-панели

В нижней части панели раздел «Лог» — весь текст скопировать целиком
(кнопка очистки — `btn_clear_log`, не нажимать до копирования).
Дополнительно открыть консоль отладки CEP (Chrome DevTools через
порт, указанный в `cep/CSXS/manifest.xml`/`.debug`, либо
`Window → Extensions` → правый клик → Inspect, если доступно в
установленной версии Premiere — уточнить точный способ под
конкретную версию) и скопировать ошибки JS, если лог панели их не
показал.

### 6.4 Состояние Premiere-проекта

- Сохранить копию `.prproj` после сбоя (не перезаписывать
  оригинал).
- Сделать скриншот таймлайна Rough Cut секвенции с видимыми
  маркерами `RC_SYNC_*`.
- Зафиксировать точное имя и ID активной секвенции на момент сбоя.
