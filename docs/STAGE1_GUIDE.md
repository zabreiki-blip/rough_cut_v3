# Stage 1: Руководство по работе со сценарием

## Общая схема

```text
сценарий → нормализация → проверка и подтверждение → scenario_prepared.json
         → TTS → speaker/revisions/rev_NNNN/zk*.wav → сборка
```

CLI-команды ниже работают с указанными путями отдельно от истории редакций.

---

## Версии сценария в веб-интерфейсе

Версии изолированы каталогом проекта и работают для любого допустимого имени
проекта, а не для одного заранее заданного проекта.

### Жизненный цикл редакции

1. Загрузи первый сценарий, создай нормализацию, проверь блоки и сохрани её.
2. При первом импорте нового сценария текущее состояние автоматически станет
   baseline `rev_0001` вместе со снимком исходного файла.
3. Новый сценарий из `ЗАГРУЗИТЬ/Сценарии` импортируется в следующий уникальный
   `rev_NNNN`. Родителем становится активная редакция, поэтому diff строится от
   той версии, с которой пользователь действительно работает.
4. Импортированная редакция остаётся отдельным черновиком. Просмотри изменения
   (`unchanged`, `moved`, `edited`, `added`, `removed`, изменение типа или
   спикера) и нажми «Открыть», чтобы сделать её активной.
5. После открытия проверь нормализацию и подтверди её. TTS и последующие этапы
   принимают только подтверждённую актуальную проекцию.

Импорт не перезаписывает активный `work/`. При переключении восстанавливаются
снимки нормализации, подготовленного сценария, карты озвучки, sync matches и
таймлайна, если они были сохранены для редакции. Неизменившиеся и перемещённые
блоки сохраняют стабильный UID, поэтому их озвучка и подтверждённые совпадения
могут быть переиспользованы. Файлы
`speaker/revisions/<revision_id>/zkN.wav` — позиционные алиасы данной редакции;
неизменяемые аудиоактивы находятся в `speaker/assets/<block_uid>/`.

### Целостность и восстановление

`GET /stage4/revisions` возвращает не только историю, но и поле `integrity`.
Если указатель активной редакции отсутствует, неизвестен или не совпадает с
`scenario_revision_id` в рабочей нормализации, импорт и обычное переключение
блокируются. В интерфейсе выбери известную редакцию и нажми «Восстановить»:
текущие `work/` и позиционные WAV сначала копируются в
`versions/recovery/<timestamp>/`, затем выбранная редакция разворачивается как
активная.

Не запускай импорт, переключение или восстановление во время активной задачи
нормализации, TTS, sync либо Stage 3: API вернёт `409`. Ограничение действует
внутри одного проекта; задачи других проектов не блокируют его историю.

CLI-команды ниже обрабатывают переданные пути напрямую и не создают историю
`rev_NNNN`. Для полного жизненного цикла редакций используй веб-интерфейс или
Stage 4 API.

## 1. Подготовка сценария

### Поддерживаемые форматы
- `.docx` (рекомендуется — поддержка форматирования)
- `.doc` (legacy, требует `catdoc`)
- `.txt`, `.md` (только текст)

### Разметка закадрового текста

Анализатор использует **5 стратегий** в порядке приоритета. Как только одна сработала — остальные пропускаются.

#### Стратегия 1: Ручные маркеры в тексте
Форматы (все case-insensitive):

| Формат | Пример |
|--------|--------|
| Нумерованный | `ЗК1 Текст озвучки...` |
| Нумерованный с разделителем | `ЗК1: Текст озвучки...` |
| Префикс | `ЗК: Текст озвучки...` |
| Блочный | `[[VO]]Текст озвучки...[[/VO]]` |

Синонимы: `ЗК`, `ЗАКАДР`, `VO`, `NARRATOR`.

**Многострочные блоки:** текст после маркера захватывается до:
- пустой строки
- следующего маркера (`ЗК`, `ЗАКАДР`, `VO`)
- метки спикера (`СНХ`, `СПИКЕР`, `ВЕДУЩИЙ`)

#### Стратегия 2: Заливка в Word (highlight)
- Выдели цветом (Highlight / заливка текста) нужные абзацы в Word.
- Не надо ничего менять в тексте — работает по форматированию.

#### Стратегия 3: Форматирование .docx (bold)
- Требуется контраст: ≥3 жирных и ≥3 нежирных абзацев.
- Абзацы с >50% полужирных символов не считаются закадровыми.
- **Жирное = НЕ закадр** (ведущий, СНХ, заголовки).
- **Нежирное = закадр** (если не техметка/интервью).

#### Стратегия 4: LLM (OpenRouter)
- Срабатывает если ни одна из стратегий выше не дала результата и есть `OPENROUTER_API_KEY`.
- Текст разбивается на чанки по ~6000 символов.
- LLM (temperature=0.2) определяет, что является закадром.
- Если LLM упадёт на каком-то чанке — для него используется fallback.

#### Стратегия 5: Fallback
- Берёт все абзацы, фильтруя спикерские реплики и техметки.
- Разбивает длинные абзацы (>300 символов) по предложениям.

> **Важно:** Маркеры `ЗК1` (стратегия 1) имеют приоритет над заливкой и жирным форматированием `.docx`.

## 2. Что автоматически исключается

### Спикерские метки
`СПИКЕР:`, `СНХ:`, `ВЕДУЩИЙ:`, `СНХ Имя Фамилия, ...`
(с номерами: `СПИКЕР-1:`, `ВЕДУЩИЙ 2:`)

### Технические метки
`ВИДЕО`, `ЛАЙФ`, `ВНИМАНИЕ`, `ШАПКА`, `ОТБИВКА`, `ТИТР`, `ПЛАШКА`, `ГРАФИКА`, `КАРТА`, `ФОТО`, `ВОТ ССЫЛКА`

### Интервью / синхроны
- Таймкоды: `[06:34]`, `12:45:00`
- Ремарки: `(…)`, `(...)`
- Короткие ALL-CAPS строки (<50 символов)

### Очистка текста
- Спикерские метки внутри текста убираются.
- Техметки внутри текста убираются.
- Пробелы и переносы нормализуются.
- Блоки короче 5 символов отбрасываются.

---

## 3. Объединение и нумерация блоков

1. **Короткие блоки** (<40 символов) объединяются со следующим.
2. **Глобальный лимит** `MAX_ZK_BLOCKS` (env, default=40, min=1) — если блоков больше, они группируются.
3. **Перенумерация** — всем блокам присваиваются ID `zk1`, `zk2`, ..., `zkN`.

## 4. Команды

### Анализ сценария
```bash
scripts/analyze-script \
  --in projects/<project>/input/scenario.docx \
  --out projects/<project>/work/scenario_prepared.json

# Без LLM (только локальные стратегии):
scripts/analyze-script --in ... --out ... --no-llm
```

### Синтез TTS
```bash
scripts/synthesize-tts \
  --in projects/<project>/work/scenario_prepared.json \
  --out projects/<project>/speaker \
  --gender female

# Dry run (без API, файлы-заглушки):
scripts/synthesize-tts --in ... --out ... --dry-run
```

Уже озвученные блоки пропускаются (проверяется валидность WAV).

### Озвучка одной фразы
```bash
scripts/synthesize-phrase \
  --text "Тест дикторского голоса" \
  --out projects/<project>/speaker \
  --file phrase_preview \
  --provider macos --gender female
```

### Валидация и манифест
```bash
scripts/validate-stage1 \
  --in projects/<project>/work/scenario_prepared.json \
  --speaker projects/<project>/speaker \
  --manifest projects/<project>/speaker/manifest.json
```

**Проверки:**
- Формат ID: `^zk\d+$`
- Нет дубликатов
- Последовательность `zk1..zkN` без пропусков
- Все WAV файлы существуют и валидны (≥44 байта)
- Warning: длительность < 350 мс
- Warning: слишком тихий файл (RMS ≤ порога)

Последний статус normalization/TTS/sync job атомарно сохраняется в `work/`.
После рестарта незавершённая задача показывается как прерванная и может быть
безопасно перезапущена с сохранённых артефактов.

Финальная проверка начинается с экспорта WAV внутри проекта. Estimate принимает
`project`, `audio_path`, при необходимости `backend` и `cloud_options`, возвращает
`duration`/`duration_sec`, `planned_chunks`, `estimated_cost_usd` (точную
десятичную строку), `cost_limit_usd`, `enforced`. Start принимает те же параметры,
снимок `source_sequence`/`assembly_layout` и `confirmed_estimate_usd` без
округления. При изменении оценки возвращается HTTP 409 и требуется повторное
подтверждение; успешный Start возвращает HTTP 202 с `job_id`/`status_url`.

`FINAL_REVIEW_TIMEOUT_SECONDS=7200` — общий срок final review с момента принятия,
включая очередь ASR; истечение даёт `failed` и ошибку timeout. Отдельный
HTTP-запрос ограничен меньшим из 900 секунд и оставшегося срока задачи.
`ROUGH_CUT_MAX_USD_PER_JOB=0` отключает облачный лимит,
`ROUGH_CUT_CLOUD_ASR_USD_PER_MINUTE_ESTIMATE=0` означает неизвестную цену минуты.
Положительный лимит требует положительной оценки; расчёт учитывает перекрытия
чанков, а резервирование — каждую попытку провайдера. Превышение оценки
возвращает HTTP 409 до запуска. Для sync лимит общий по всем исходникам одной
задачи; локальный ASR имеет нулевую облачную оценку. Оценка без включённого
лимита используется для учёта и не задаёт потолок платежа.

Статус содержит `estimated_cost_usd`, `cost_limit_usd`, известную `cost_usd`,
резерв `reserved_cost_usd`, флаг `cost_pending`. Неизвестная цена остаётся
резервом, даже нулевая оценка может иметь `cost_pending=true`. Cancel/timeout
сохраняют последний известный резерв в статусе задачи и pending-событии
журнала: `reserved_cost_usd` хранится отдельно от подтверждённой `cost_usd`
как десятичная строка, включая явный ноль. Следующая задача и рестарт не
стирают эту оценку; резерв не входит в подтверждённые расходы. CEP показывает
известную стоимость, резерв и предупреждение: уже отправленный запрос может
быть оплачен. Cancel активной задачи
отвечает HTTP 202 и `cancelling`, окончательный статус — `cancelled`; терминальная задача отвечает
HTTP 200 без смены статуса.

При перезагрузке CEP и смене проекта latest восстанавливает задачу; после
рестарта сервера активная сохранённая задача становится `interrupted`.
Панель продолжает опрос активной задачи, повторяет ошибки через 3, 6, 12, 24,
30 секунд и затем предлагает Retry с тем же job ID. Скрытие панели приостанавливает
опрос; возвращение обновляет статус. Кнопка Cancel доступна для активной задачи.
Для завершённого отчёта Apply требует совпадения активного `sequenceId` с
сохранённой секвенцией. Apply принимает `project`, `request_id` (до 128 символов),
возвращает `iteration` и `corrections`. Повтор запроса с тем же ID возвращает ту
же итерацию, ID от другой задачи даёт HTTP 409; новый явный Apply получает новый
ID для новой итерации после возвращения к исходной секвенции и обновления
статуса панели. Без ID каждый запрос создаёт новую итерацию. API готовит
данные, а CEP создаёт и исправляет копию секвенции.

## Готовая запись диктора

Вместо синтеза TTS закадровые блоки можно озвучить готовой записью диктора:
один общий файл, у каждого блока свой диапазон in/out. Файлы `zkN.wav` для
блоков с записью не нужны.

1. Положите файл (WAV или MP3) в `projects/<проект>/ЗАГРУЗИТЬ/Закадр/` или
   загрузите его на вкладке «Озвучка» → «Готовая запись». Запись из нескольких
   частей кладётся несколькими файлами. Новый файл в папке находится при
   открытии вкладки (кнопка «Проверить ЗАГРУЗИТЬ/Закадр»); при подтверждённом
   сценарии сопоставление стартует само — появится «Найдена запись диктора — идёт
   сопоставление». Иначе нажмите «Сопоставить со сценарием». Статус задачи
   восстанавливается после перезагрузки страницы.
2. В таблице блоков для каждого блока показаны текст, in/out, статус и источник
   (Диктор / TTS / нет). Прослушайте диапазон кнопкой ▶ (один общий проигрыватель
   перематывается к in и останавливается на out), при необходимости поправьте
   in/out числами и нажмите «Подтвердить». Подтверждённые блоки не должны
   пересекаться.
3. Дубли: если диктор прочитал блок несколько раз, у блока стоит пометка
   «дубли: N» (или «частичный дубль»). По умолчанию выбран последний полный дубль;
   в списке «Дубли блока» можно прослушать каждый и выбрать другой.
4. Смешанный режим: у любого блока можно включить «Использовать TTS» (вернуть
   запись — «Использовать запись»). «Применить запись к редакции» публикует
   подтверждённые блоки; остальные озвучиваются TTS (если для них есть аудио)
   или остаются без озвучки («нет»). Кнопка активна, когда подтверждён хотя бы один
   блок. Громкость и тембр TTS и диктора могут отличаться — интерфейс предупреждает
   об этом при смешанной публикации.
5. Счётчик «Блоков готово» считает блоки с записью или TTS, а не файлы `zkN.wav`.
6. Если сценарий переключён на другую редакцию или разметка изменилась в другом
   окне, действие отклоняется (409), интерфейс сообщает об этом и перезагружает
   состояние; повторите действие. Для другой редакции сопоставление запускается заново.

## 7. Структура файлов проекта

```
projects/<project>/
├── ЗАГРУЗИТЬ/
│   ├── Сценарии/                 # Пользовательский inbox сценариев
│   └── Просмотровки/             # Видео и отдельный звук
├── input/
│   └── scenario.docx             # Legacy-каталог исходных сценариев
├── work/
│   ├── scenario_normalized.json # Рабочая нормализация
│   ├── scenario_raw.txt         # Извлечённый текст
│   ├── scenario_prepared.json   # Проекция для TTS
│   ├── active_revision.json     # Указатель активной rev_NNNN
│   └── voiceover_manifest.json  # Карта UID → аудиоактив
├── speaker/
│   ├── assets/<block_uid>/      # Неизменяемые WAV по UID
│   └── revisions/rev_NNNN/     # Позиционные zkN.wav данной редакции
└── versions/
    ├── scenarios/               # Manifest и снимки редакций
    ├── diffs/                   # Diff и план переиспользования
    ├── timelines/               # Снимки timeline и sync matches
    └── recovery/                # Копии перед восстановлением
```

При отдельном CLI-прогоне WAV и `manifest.json` могут лежать непосредственно
в каталоге, переданном через `--out`/`--speaker`. В веб-процессе рабочая карта
UID и активов хранится в `work/voiceover_manifest.json`.

## 8. Запуск

### Docker (рекомендуется)
```bash
scripts/bootstrap-docker
```
Gunicorn запускается без `--reload`, с четырьмя потоками и часовым timeout.
После изменения кода Docker-образ нужно пересобрать.

### Без Docker
```bash
scripts/setup-local
scripts/run-local
```

### macOS Connector (TTS через `say`)
Запускается **на хосте** (не в Docker), т.к. `say` — системная команда macOS:
```bash
scripts/run-macos-connector
```
Слушает порт **8001**. В `.env` должно быть:
```
MACOS_CONNECTOR_URL=http://host.docker.internal:8001/synthesize
```

> **Важно:** Если macOS connector не запущен, TTS с провайдером `macos` упадёт с ошибкой `Connection refused` на `host.docker.internal:8001`.

## 9. Частые проблемы

### Блоков меньше, чем ожидалось
- Проверь, какая стратегия сработала: поле `extraction_method` в JSON.
- Стратегия 3 (bold) может перехватить раньше, чем нумерованные маркеры, если в документе мало контраста по жирному. Но стратегия 2 (маркеры) имеет приоритет — если маркеры есть, она сработает.
- Короткие блоки (<40 символов) объединяются с соседними.

### Спикерские реплики попали в озвучку
- Убедись, что метки `СНХ`, `СПИКЕР`, `ВЕДУЩИЙ` написаны кириллицей, а не латиницей.
- Метка должна быть в начале строки.

### LLM не используется
- Проверь `OPENROUTER_API_KEY`.
- LLM запускается только если стратегии 1–3 не дали результата.
- Флаг `--no-llm` принудительно отключает LLM.

### Пропуски в нумерации (ЗК5 отсутствует)
- Анализатор берёт только те блоки, которые есть в документе.
- Все блоки перенумеровываются последовательно: `zk1`, `zk2`, ...
- Пропуски в исходной нумерации не вызывают ошибок.

### macOS TTS не работает в Docker
- Нужен macOS-коннектор, запускаемый на хосте.
- Установи `MACOS_CONNECTOR_URL=http://host.docker.internal:8001/synthesize`.
```bash
scripts/run-macos-connector
```

### После правки кода Flask показывает старые данные
- Перезапусти Flask-сервер (hot reload не всегда подхватывает изменения в `src/stage1/`).

## 10. Переменные окружения

| Переменная | Default | Описание |
|------------|---------|----------|
| `OPENROUTER_API_KEY` | — | Ключ для LLM и OpenRouter TTS |
| `TTS_PROVIDER` | `openrouter` | Провайдер TTS |
| `TTS_GENDER` | `female` | Пол голоса |
| `MAX_ZK_BLOCKS` | `40` | Максимум legacy-блоков после объединения |
| `MACOS_COMMAND_TIMEOUT` | `900` | Таймаут `say`/`afconvert`, секунд |
| `OPENROUTER_GEMINI_TTS_VOICE_FEMALE` | `Aoede` | Женский голос Gemini через OpenRouter |
| `OPENROUTER_GEMINI_TTS_VOICE_MALE` | `Charon` | Мужской голос Gemini через OpenRouter |
| `MACOS_TTS_RATE` | `175` | Скорость macOS TTS (wpm) |
| `MACOS_CONNECTOR_URL` | — | URL коннектора для macOS в Docker |
| `MACOS_CONNECTOR_PORT` | `8001` | Локальный порт коннектора macOS |
| `VALIDATE_MIN_WAV_DURATION_MS` | `350` | Минимум длительности WAV (warning) |
| `VALIDATE_SILENCE_RMS_THRESHOLD` | `120` | Порог тишины (warning) |

При установке LaunchAgent скрипт автоматически задаёт
`MACOS_CONNECTOR_ENV_FILE` как путь к отдельному env-файлу с правами `0600`.
В проектный `.env` эту служебную переменную добавлять не требуется.
