# Отладочный прогон rough_cut_v3 на проекте FRISKE_001 (2026-09-08)

## Цель

Таймлайн FRISKE_001 максимально близкий к сценарию + выявление косяков
приложения по ходу прогона. Пилот-чеклист B′ (платный OpenRouter smoke) в этот
прогон НЕ входит: TTS уже завершён (92 WAV, macos/Yuri), платных вызовов не
планируется.

## Текущее состояние проекта (собрано read-only)

- Сценарий: 240 блоков — 92 voiceover (озвучены), 83 sync, 65 technical;
  `status: confirmed`. Нормализация/TTS/sync/Stage3 — все `completed`
  (2026-09-07, runtime Docker, пути `/app/...`).
- Sync (cloud ASR, модель medium, 9 просмотровок — все зарегистрированы,
  9 транскриптов переиспользованы): из 89 сегментов — 34 auto_matched,
  14 confirmed, 1 needs_review, **40 not_found**.
- Среди not_found: в основном слабые лучшие альтернативы (confidence
  0.12–0.33, текст вероятно реально отсутствует в просмотровках); минимум
  один `strategy: insufficient_input` из-за **спикер-фильтра** (тема текущей
  ветки `agent/fix-speaker-filter-false-negatives`).
- Stage 3: `FRISKE_001_nested_timeline.xml` готов, 9 медиа замаплены.
- `work/final_review.wav` (сегодня 11:16, ~82 сек, stereo 48 кГц) есть, но
  `final_review_job_status.json`/`final_review_report.json` НЕТ → job не
  стартовал. Наиболее вероятная причина: backend в Docker крутится со старым
  образом без final-review маршрутов → 404 на `POST /stage2/final-review/start`.
  Альтернативы: backend не был поднят; 409 «still being exported».
- Пользователь готов экспортировать свежий WAV через CEP-панель («Проверить
  собранный таймлайн»); секвенция в Premiere уже собрана и conform-нута.

## Решения (подтверждены пользователем)

1. Runtime: **Docker compose с пересборкой** (`docker compose up -d --build`)
   — рабочий способ прошлых прогонов; faster-whisper в контейнере = транскрипция
   final review бесплатно; пересборка заодно проверяет сборку образа с новым
   кодом (аудитом не проверялась).
2. 40 not_found: **полный разбор** — анализ причин, повторный матчинг на
   готовых транскриптах (бесплатно), ручные подтверждения в UI.
3. Premiere: секвенция готова; пользователь сам водит Adobe.
4. Порядок: сначала финальная проверка на текущем состоянии (пользователь
   экспортирует WAV сейчас), затем работа с матчингом; обновление таймлайна
   и секвенции — точка решения по итогам diff-анализа.
5. Платные API — только с явного разрешения; в базовом плане не нужны
   (транскрипты переиспользуются, final review транскрибируется локально
   в контейнере).

## Известные ловушки (из аудита 2026-09-08 — ловить вживую)

- P1: `_apply` не сверяет `report["job_id"]` (`api_final_review_routes.py:81–97`)
  — два job в одном проекте = apply чужих corrections. Прогон создаст ≥2 job
  (базовый + после обновления таймлайна) → проверить curl'ом на первом job.
- P2: нет cancel у final-review; poll в панели без ретрая
  (`main.js:1600–1620`); apply после перезагрузки панели молчит
  (`main.js:1689–1691`).
- P2: `_start` без pre-check `full_timeline.json` — у FRISKE файл есть
  (старый формат, без `speech_in/out` — fallback на `source_in/out` должен
  сработать; проверить).
- Повторный матчинг перезапишет `sync_matches.json` — сохранятся ли 14
  confirmed, неизвестно → бэкап обязателен, потеря = отдельный косяк.
- Длительность: старый WAV ~82 сек подозрительно короткий; сверять
  длительность свежего WAV с ожидаемой длительностью `full_timeline.json`.

## Задачи (по порядку)

### Этап 0. Подготовка (агент; НЕ трогать проект до бэкапа)

1. Бэкап состояния: `cp -R projects/FRISKE_001/work
   ~/Documents/AI/rough_cut_v3_debug_backups/FRISKE_001_work_2026-09-08/`
   (вне репозитория и вне `projects/`, чтобы не появиться «проектом» в UI).
   Плюс `speaker/manifest.json` и `scenario_normalized.json` (они в work/,
   уже входит). Проверить чтением.
2. Пересборка и старт: `docker compose up -d --build` (лог сборки сохранить).
   `docker compose config --quiet` уже проходил; если сборка упадёт — это
   первый косяк в отчёт, fallback: локальный запуск после `scripts/setup-local`
   (транскрипции тогда cloud, спросить пользователя).
3. Health-проверки: `curl -s http://127.0.0.1:8000/health`;
   проба маршрута: `curl -s -o /dev/null -w '%{http_code}'
   http://127.0.0.1:8000/stage2/final-review/jobs/probe` → ожидание 404 c
   JSON `{"ok":false,...}` (маршрут есть), не HTML-404 (старый образ).
4. Preflight whisper в контейнере: `docker compose exec stage1-api python -c
   "import faster_whisper"` (+ наличие модели medium в кэше volume).
5. Запустить сбор логов: `docker compose logs -f stage1-api` → tee в файл
   бэкап-каталога. Сказать пользователю, что можно нажимать кнопку в панели.

### Этап 1. Финальная проверка — базовая (пользователь в Premiere + агент мониторит)

6. Пользователь: активная conform-нутая Rough Cut секвенция → «Проверить
   собранный таймлайн». Агент параллельно: следить за логом backend,
   `work/final_review_job_status.json`, `final_review_report.json`.
7. Контроль длительности: длительность свежего WAV против суммы
   `full_timeline.json` (если WAV снова ~82 сек при большом таймлайне —
   экспортируется не та/не вся секвенция; отдельный косяк host-экспорта).
8. Дождаться completed (poll ~3 сек). Зафиксировать summary
   (expected_segments/findings/missing/truncated/automatic_corrections).
   Ожидание: часть sync-блоков даст `missing` (40 пробелов в conform) —
   это валидное поведение фичи, не сбой.
9. Особые проверки из аудита: (a) сетевой сбой poll — не моделировать
   принудительно, но заметить, если случится; (b) apply: НЕ нажимать до
   этапа 4 (сначала работа с матчингом); вместо этого проверить P1 curl'ом
   позже, когда появится второй job.

### Этап 2. Анализ 40 not_found (агент, read-only)

10. Сформировать таблицу: block_uid, тип стратегии (fallback_full /
    near_timecode / insufficient_input), лучший confidence, спикер блока,
    список отфильтрованных по спикеру источников. Классифицировать:
    (a) спикер-фильтр закрыл кандидатов (кандидат в баги ветки), (b) слабый
    лучший матч <0.33 — вероятно материала нет, (c) пограничные 0.30–0.50 —
    кандидаты на ручное прослушивание.
11. Сверить тексты пограничных блоков с alternatives глазами — есть ли
    смысл в ручном подтверждении.

### Этап 3. Повторный матчинг (мутация; после бэкапа)

12. UI «Найти СНХ автоматически», движок «Локально» (faster-whisper в
    контейнере; транскрипты переиспользуются — transcribed: 0 ожидаемо).
    Настройки по умолчанию — цель увидеть поведение нового кода (паддинги
    2.0/1.5, speech_in/out, фиксы спикер-фильтра).
13. Diff-отчёт до/после: статусы (auto/confirmed/needs_review/not_found),
    сдвиги source_in/out у ранее сматченных, сохранность 14 confirmed
    (если потеряны — восстановить из бэкапа `sync_matches.json`, записать
    косяк с file:line).
14. Пользователь: подтвердить 1 needs_review и пограничных кандидатов
    через «Прослушайте диапазон…» (PATCH sync-matches).

### Этап 4. Точка решения: обновление таймлайна и секвенции

15. Если набор/диапазоны изменились существенно: «Build Timeline» →
    переэкспорт XML → обновить секвенцию в Premiere (повторный conform,
    идемпотентность по маркерам — §4.1 чеклиста) → **повторная финальная
    проверка** (этап 1 на новом состоянии; старый job остаётся в реестре →
    это момент для curl-проверки P1: apply первого job после завершения
    второго должен дать чужие corrections — подтвердить/опровергнуть).
    Если изменения косметические — обновление не делать, зафиксировать
    решение и причину.

### Этап 5. Отчёт прогона

16. Собрать: лог backend, diff-отчёт матчинга, summary обеих финальных
    проверок, список косяков с file:line (включая итог по P1/P2 аудита,
    живым проявлениям), артефакты по §6 чеклиста при сбоях. Записать в
    `docs/` отдельным отчётом прогона (после согласования с пользователем).

## Валидация

- Backend поднят с новым кодом (проба маршрута вернула JSON-404).
- Финальная проверка завершилась `completed` с отчётом; длительность WAV
    соотносится с таймлайном.
- Diff-отчёт матчинга сформирован; 14 confirmed не потеряны (или
    восстановлены + косяк зафиксирован).
- Каждый косяк имеет file:line и шаг прогона, на котором проявился.

## Риски / границы

- Реальные данные: мутируются только `work/*` (job-статусы, sync_matches,
  full_timeline, final_review артефакты); медиа и speaker только читаются;
  всё восстановимо из бэкапа этапа 0.
- Сборка Docker-образа новым кодом не гарантирована (аудит не проверял) —
  падение сборки = находка, не блокер (fallback локальный venv).
- faster-whisper в контейнере не проверялся живым транскрибированием в этом
  прогоне (прошлый sync шёл cloud) — preflight этапа 0.4 обязателен; при
  провале — cloud только с разрешения пользователя (платно, ~1.5 мин аудио).
- Правки кода по найденным косякам — вне этого прогона (отдельное решение
  после отчёта).
