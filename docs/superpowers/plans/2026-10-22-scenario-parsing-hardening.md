# Разбор сценариев после SPAS_DM_1s_001 — план доработки

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** исправить системные ошибки выделения блоков, текста и таймкодов,
используя SPAS_DM_1s_001 как контрольный сценарий.

**Architecture:** общий структурный разбор перед классификацией, сохранение
исходного текста, контекст сцен и единая проверка перед подтверждением.
Работы выполнять небольшими совместимыми изменениями существующего workflow.

**Tech Stack:** Python / Flask / dataclasses / JavaScript / pytest / Node.

**Spec:** [Цель, факты и критерии приёмки](../specs/2026-10-22-scenario-parsing-hardening-design.md).

Статус: план подготовлен 22.10.2026; продуктовый код и данные проекта не изменены.

## Global Constraints

- Исходный текст неизменяем; без художественного редактирования речи.
- Авторский номер метки не является UID; повтор номера не объединяет блоки.
- Сохранять ручные правки и поддерживать чтение прежних сценариев.
- CEP заморожен; ASR и общий инфраструктурный рефакторинг вне первой очереди.
- Платные вызовы не нужны для регрессионных тестов разбора.
- Полный пользовательский DOCX не добавлять в Git; использовать минимальные
  обезличенные тестовые примеры и локальную полную контрольную разметку.
- Каждое исправление: воспроизводимый тест → проверка падения → изменение
  → проверка прохождения → отдельный обзор diff. Коммиты разделять по задачам.

## Review Focus

- Число после метки может быть частью речи: `ЗК 1915 год…` должно сохранить год (задача 2).
- Время в круглых скобках и точки в датах не являются разделителями роли (задача 3).
- Склейка может возвращаться назад по исходнику; нельзя сортировать её по времени (задача 3).
- Короткое `— Да` принадлежит сцене, но не доказывает личность героя (задача 4).
- Повторный разбор после ручной правки и поздний ответ сервера не должны затирать правку (задачи 6–7).

  фрагментами с раздельными входами. `00:05:20–00:05:40 Первый текст`
  остаётся одним диапазоном. Покрыть обратный порядок времени и дату в речи.
- [ ] Для LIFE сериализовать части в существующее `sync_fragments` как
  `text/timecode_start/timecode_end`; пустой список сохраняет старое поведение.

- [ ] Добавить контрактный тест `test_life_splice_survives_normalization_and_timeline`:

  сохранения/чтения даёт две единицы сопоставления и два LIFE-сегмента,
  тексты `Первый текст`/`Второй текст`, входы `00:05:20`/`00:52:40`,
  пустые выходы, общий parent UID и разные стабильные fragment ID.

Результат: каждая явная монтажная часть доходит до таймлайна с правильным текстом

## Порядок и критерий окончания

1 → 2 → 3 → 4 → 5 образуют первую поставку: корректность разбора.
6 и 7 выполняются после стабилизации контракта; независимые части можно
делегировать параллельно. 8 — обязательная приёмка общей версии.

Полная перепись приложения создаёт слишком широкий объём изменений.
Одни точечные regex-правки оставляют дублирующиеся решения о границах текста.
Рекомендация — последовательное выделение общего структурного разбора с
регрессиями на каждом шаге. Оценку сроков уточнять после эталонной разметки;
факт выполнения задачи не подменять статусом `completed` фонового задания.
