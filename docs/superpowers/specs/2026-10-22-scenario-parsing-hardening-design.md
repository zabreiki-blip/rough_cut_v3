# Системная доработка разбора сценариев после SPAS_DM_1s_001

Дата: 22.10.2026. Статус: предложение для обсуждения, реализация не начата.

## Цель и границы

Пользователь обозначил главный приоритет: разбор сценария — блоки, текст,
таймкоды. Цель — корректно получать монтажную структуру из разных авторских
форматов, сохранять содержание и показывать неоднозначности до озвучки.
SPAS_DM_1s_001 становится контрольным примером для общих правил.

Стек сохраняется: Python, Flask, dataclass-модели, браузерный JavaScript,
pytest и существующие Node behavior tests. CEP заморожен согласно TECH_DEBT.
Изменение ASR, подбор другой LLM и общий инфраструктурный рефакторинг не входят
в первую очередь. Проверка передачи данных в Stage 2/3 входит.

Пять классов дефектов — ЗК без двоеточия, ложный герой, LIFE с таймкодом,
роль с таймкодом, LIFE со склейкой — воспроизведены локально текущим кодом
без LLM, с временными файлами и пустой временной памятью правил.
Контрольный `ЗК14: Текст` разбирается правильно, `ЗК14 Текст` — неправильно.
Каждый из пяти ошибочных минимальных примеров проходит
`validate_for_confirmation` без замечаний. Сохранённый полный SPAS получает
29 замечаний и уже блокируется существующим валидатором.

`completed` обозначает завершение задачи, а не подтверждение сценария.
Интерфейс уже объединяет предупреждения блоков и документа и имеет навигацию
по проблемам. Эти механизмы нужно расширить; их отсутствие не является находкой.
Данных об озвучке или синхронизации SPAS в папке проекта пока нет.

## Предлагаемое устройство

Сохранить внешний workflow и поэтапно выделить структурный разбор из
`normalizer.py`: исходный текст → токены меток/таймкодов/склеек → поля блока
→ контекст соседних блоков → классификация → проверка → подтверждение.
Чистые функции разбора не обращаются к LLM и не записывают проект.

Исходный текст неизменяем. У каждого выделенного элемента сохраняется связь
с диапазоном исходного текста. Метаданные удаляются из речевого текста только
после распознавания; художественное редактирование речи не выполняется.
Номер авторской метки не используется как UID: повтор `ЗК7` не объединяет блоки.

Служебные метки и таймкоды имеют приоритет над эвристикой имени. LLM разрешает
неоднозначную классификацию, но не переписывает авторский текст и не исправляет
поля, однозначно извлечённые парсером. Контекст диалога хранит связь со сценой;
при отсутствии данных личность говорящего остаётся неопределённой.

Отличать диапазон `00:05:20–00:05:40` от склейки `00:05:20 … + 00:52:40 …`.
Сохранять порядок фрагментов, даже если исходные таймкоды идут назад.
Дата, год и число в речи не становятся меткой или таймкодом автоматически.
Для LIFE использовать существующее поле `sync_fragments` со структурой
`text/timecode_start/timecode_end`. Пустое поле сохраняет старое поведение.
Обновить оба потребителя: `_sync_alignment_units` в API и LIFE-ветку
`parse_normalized_timeline`. Два явных фрагмента должны дать две единицы
сопоставления и два LIFE-сегмента с общим родительским UID и разными ID.

## Приёмка

- Все перечисленные воспроизводимые дефекты закрыты регрессионными тестами.
- В контрольных примерах весь речевой текст сохранён в исходном порядке;
  удалённые из него части учтены как служебные элементы.
- Во всех 34 отмеченных ЗК-блоках SPAS нет служебной метки в TTS-тексте;
  авторские числа, даты и повтор номера сохранены корректно.
- Таймкоды не попадают в роли/имена; явно заданные склейки не становятся
  длинными диапазонами и сохраняются до таймлайна.
- Неоднозначные случаи требуют явного решения; процент уверенности LLM
  сам по себе не даёт разрешения на озвучку.
- Ручные исправления, UID, версии и исходные проекты не теряются при повторе.
- Старые форматы проверены на существующих тестах; полный SPAS проверен
  отдельно по эталонной разметке. Порог «95% достаточно» для потери текста
  или ошибочных таймкодов не используется.
