# Stage 4 — версии сценария и инкрементальная пересборка

## Цель

Поддержать новые редакции сценария без повторной обработки всего проекта.
Система должна сохранять уже выполненную работу и пересчитывать только то, что
реально изменилось.

Типичные изменения редакции:

- сокращение, расширение или перестановка блоков;
- добавление и удаление закадрового текста;
- добавление и удаление СНХ;
- изменение текста цитаты существующего спикера;
- появление нового спикера и новой просмотровки;
- добавление хроники, фрагментов фильмов, фотографий и графики;
- превращение ЗК в СНХ или СНХ в ЗК;
- разделение одного блока на несколько и объединение нескольких блоков.

## Главный принцип

Новая версия собирается по модели **copy-on-write**:

1. предыдущая подтверждённая версия остаётся неизменной;
2. система сопоставляет старые и новые сценарные блоки;
3. готовые артефакты переиспользуются по fingerprint;
4. пересчитываются только изменившиеся зависимости;
5. создаётся новая версия таймлайна, не перезаписывающая старую.

Перестановка готовых блоков должна стоить только времени генерации нового XML.
Она не должна повторно запускать TTS, Whisper или поиск СНХ.

## Структура проекта

Скелет создаётся автоматически для каждого проекта:

```text
projects/<project>/
├── input/                         # текущий загруженный сценарий
├── speaker/                       # совместимость с текущим Stage 1
├── media/
│   ├── reviews/                   # просмотровки интервью
│   ├── archive/                   # хроника
│   ├── films/                     # фильмы и программы
│   ├── photos/                    # фотографии и документы
│   └── graphics/                  # готовая графика и иллюстрации
├── versions/
│   ├── scenarios/                 # неизменяемые редакции сценария
│   ├── diffs/                     # результаты сравнения редакций
│   └── timelines/                 # манифесты и XML каждой версии
└── work/                          # вычисляемые кэши и активное состояние
    ├── transcripts/
    ├── sync_audio/
    └── artifacts/                 # будущий content-addressed cache
```

Каталоги `media/` и `versions/` являются данными проекта и не добавляются в Git.

## Сущности и идентификаторы

### ScenarioRevision

Неизменяемая редакция сценария:

```json
{
  "revision_id": "rev_0003",
  "parent_revision_id": "rev_0002",
  "source_file": "scenario_v3.docx",
  "source_sha256": "...",
  "created_at": "...",
  "status": "draft|confirmed|exported"
}
```

### ScenarioBlock

Каждый логический блок получает стабильный `block_uid`, который сохраняется
между редакциями, даже если блок переместили.

Дополнительные поля:

- `revision_id`;
- `block_uid`;
- `parent_block_uid` для split/merge;
- `type`: `voiceover`, `sync`, `host`, `archive`, `film`, `photo`, `graphics`;
- `speaker`;
- `text`;
- `media_hint`;
- `content_fingerprint`;
- `artifact_refs`;
- `locked_fields` для подтверждённых редактором решений.

### Artifact

Любой дорогой результат хранится отдельно от версии сценария:

- WAV закадра;
- Whisper word index;
- подтверждённый диапазон СНХ;
- placeholder;
- preview;
- XML таймлайна.

Артефакт имеет:

```json
{
  "artifact_id": "...",
  "kind": "tts|whisper|sync_match|preview|timeline",
  "fingerprint": "...",
  "inputs": ["..."],
  "created_at": "...",
  "path": "..."
}
```

## Сопоставление двух редакций

Сравнение выполняется не по порядковым номерам `ЗК1`/`СНХ1`, а по содержанию и
контексту.

Этапы:

1. точное совпадение стабильного UID, если он уже сохранён в документе;
2. точное совпадение нормализованного текста, типа и спикера;
3. сопоставление перемещённых блоков по fingerprint;
4. fuzzy-сопоставление отредактированного текста;
5. определение split/merge;
6. ручное подтверждение неоднозначных соответствий.

Результат для каждого блока:

- `unchanged` — не требует действий;
- `moved` — меняется только позиция в таймлайне;
- `edited` — пересчитываются зависящие артефакты;
- `added` — создаются новые артефакты;
- `removed` — блок отсутствует только в новой версии;
- `type_changed` — меняется вычислительный pipeline;
- `speaker_changed` — требуется поиск в другом источнике;
- `split` / `merged` — сохраняется связь с исходными блоками;
- `ambiguous` — требуется решение пользователя.

## Матрица минимальной пересборки

| Изменение | Что сохраняем | Что пересчитываем |
|---|---|---|
| Блок переставили | WAV, Whisper, In/Out | XML новой версии |
| Блок удалили | Все старые артефакты | XML новой версии |
| ЗК сократили или изменили | Старый WAV в старой версии | Один новый WAV |
| Добавили ЗК | Все существующие артефакты | Один новый WAV |
| Изменили текст СНХ | Whisper просмотровки | Match только этой фразы |
| Добавили СНХ старого спикера | Whisper просмотровки | Match новой фразы |
| Переставили части СНХ | Найденные In/Out | XML новой версии |
| Удалили СНХ | Whisper и старый match | XML новой версии |
| Добавили нового спикера | Все старые транскрипты | Whisper новой просмотровки |
| Заменили ЗК на СНХ | Старый WAV в старой версии | Match нового СНХ |
| Заменили СНХ на ЗК | Whisper и старый match | Новый WAV |
| Добавили хронику/фильм | Вся существующая медиатека | Индекс только нового файла |
| Изменили подпись/описание медиа | Сам медиафайл | Только metadata/index |

## Fingerprints и инвалидизация

### TTS fingerprint

Зависит от:

- нормализованного текста;
- голоса;
- модели и настроек TTS;
- скорости;
- версии постобработки.

Если fingerprint совпадает, WAV переиспользуется независимо от номера и позиции
блока.

### Whisper fingerprint

Зависит от:

- content fingerprint медиафайла;
- Whisper backend/model;
- языка;
- параметров распознавания.

Переименование или перемещение неизменившегося файла не должно запускать
Whisper повторно, если content fingerprint совпадает.

### Sync-match fingerprint

Зависит от:

- нормализованного текста цитаты;
- выбранной просмотровки;
- fingerprint Whisper-транскрипта;
- параметров matcher;
- timecode hint, если он указан.

Перемещение блока внутри сценария не входит в fingerprint.

### Timeline fingerprint

Зависит от порядка блоков, выбранных артефактов, длительностей и параметров
sequence. Любое структурное изменение создаёт новый timeline manifest/XML, но
не инвалидирует исходные артефакты.

## СНХ и наследование контекста

Безымянный блок `СНХ` наследует спикера последнего явно подписанного синхрона.
Он считается самостоятельным монтажным фрагментом этого интервью:

- не обязан продолжать предыдущий source timecode;
- может быть взят из более раннего или более позднего места;
- может менять порядок относительно исходной речи;
- может пересекаться с диапазоном другого сценарного блока;
- ищется независимо по всему транскрипту выбранной просмотровки.

Ручная смена спикера или источника всегда имеет приоритет над наследованием.

## Новые спикеры

При появлении нового имени система:

1. ищет подходящую просмотровку в `media/reviews`;
2. предлагает найденное соответствие по имени файла;
3. если файла нет — показывает блокирующее состояние «нужна просмотровка»;
4. после добавления файла запускает ffprobe и Whisper только для него;
5. сопоставляет только новые/изменённые цитаты этого спикера;
6. создаёт новый `RC_SRC_<имя>`.

Старые спикеры и их транскрипты не затрагиваются.

## Хроника, фильмы, фотографии и графика

### Описание в сценарии

Поддерживаем явные блоки:

```text
ХРОНИКА: Москва, 1930-е
ФИЛЬМ: «Баня», 00:14:20–00:14:34
ФОТО: Лиля Брик и Владимир Маяковский
ГРАФИКА: карта поездки в Париж
```

### MediaAsset

Для каждого источника храним:

- `asset_id` и content fingerprint;
- категорию;
- название и альтернативные названия;
- путь;
- длительность, fps и размеры;
- описание сцены;
- встроенный timecode;
- правообладателя, источник и ограничения;
- Whisper-транскрипт при наличии речи;
- связанные сценарные блоки.

Если сценарий содержит точный файл и timecode, диапазон создаётся автоматически.
Если указано только описание, система показывает кандидатов. Неоднозначный
медиафайл не выбирается молча.

В XML используются отдельные source sequences:

```text
RC_ARCHIVE_<name>
RC_FILM_<name>
RC_PHOTO_<name>
RC_GRAPHICS_<name>
```

## Пользовательский процесс

1. Пользователь загружает новую редакцию DOCX.
2. Система сохраняет её как новую `ScenarioRevision`.
3. Выполняется сравнение с выбранной предыдущей редакцией.
4. Интерфейс показывает сводку:

   ```text
   Без изменений       83
   Переставлено        11
   Изменено            12
   Добавлено            7
   Удалено              4
   Нужен новый спикер   2
   Нужна хроника        5
   Неоднозначно         3
   ```

5. Пользователь подтверждает неоднозначные связи и новые источники.
6. Система строит execution plan с оценкой времени и стоимости.
7. Запускаются только необходимые задачи.
8. Создаётся новый timeline manifest и XML.
9. Предыдущая версия остаётся доступной для сравнения и отката.

## Интерфейс

### Экран редакций

- список версий и их статусов;
- выбор базовой версии для сравнения;
- загрузка новой редакции;
- визуальный diff блоков;
- фильтры по типу изменения;
- подтверждение ambiguous/split/merge;
- оценка времени до запуска обработки.

### Execution plan

Перед запуском показываем:

```text
Переиспользуется:
  83 блока
  61 WAV
  9 Whisper-транскриптов
  48 подтверждённых СНХ

Будет выполнено:
  4 новых WAV
  3 повторных поиска СНХ
  1 новый Whisper-транскрипт — примерно 42 минуты
  1 новый XML
```

### Защита ручной работы

- подтверждённые `In/Out` блокируются;
- ручная связь блока и источника имеет приоритет;
- изменение текста не удаляет старое решение;
- система предлагает сохранить диапазон, сбросить его или создать новый match;
- массовая инвалидизация требует отдельного подтверждения.

## Версии таймлайна

Каждая подтверждённая редакция создаёт собственную sequence:

```text
ROUGH_CUT_BRIK_V001
ROUGH_CUT_BRIK_V002
ROUGH_CUT_BRIK_V003
```

Общие `RC_SRC_*`, `RC_ARCHIVE_*` и другие исходные sequences переиспользуются.
Старая sequence никогда не перезаписывается автоматически.

Для каждой версии сохраняются:

- `scenario_revision_id`;
- diff с родительской версией;
- execution plan;
- список использованных artifacts;
- timeline manifest;
- экспортированный XML;
- результаты проверки.

## API — предварительный контракт

```text
POST /stage4/revisions/import
GET  /stage4/revisions
GET  /stage4/revisions/<revision_id>
POST /stage4/revisions/<revision_id>/compare
GET  /stage4/diffs/<diff_id>
POST /stage4/diffs/<diff_id>/resolve
POST /stage4/revisions/<revision_id>/plan
POST /stage4/revisions/<revision_id>/build
GET  /stage4/jobs/<job_id>
GET  /stage4/revisions/<revision_id>/export/xml
```

Mutating endpoints используют revision checks, чтобы две вкладки не могли
молча перезаписать решения друг друга.

## Этапы разработки

### Этап 4.1 — хранилище редакций

- неизменяемые ScenarioRevision;
- стабильные block UID;
- импорт новой редакции;
- список и восстановление версий;
- тесты обратной совместимости с текущим `scenario_normalized.json`.

### Этап 4.2 — semantic diff

- unchanged/moved/edited/added/removed;
- split/merge;
- speaker/type changes;
- ambiguous review;
- сохранение ручных решений diff.

### Этап 4.3 — dependency graph

- fingerprints артефактов;
- execution plan;
- точечная инвалидизация;
- оценка времени и стоимости;
- повторное использование текущих TTS/Whisper/match caches.

### Этап 4.4 — версионная сборка

- timeline manifest на каждую редакцию;
- `ROUGH_CUT_<project>_V###`;
- сравнение длительности и структуры;
- rollback без пересчёта.

### Этап 4.5 — медиатека

- archive/films/photos/graphics catalog;
- metadata и права;
- точные timecode references;
- подбор кандидатов по описанию;
- `RC_ARCHIVE_*`, `RC_FILM_*`, `RC_PHOTO_*`, `RC_GRAPHICS_*`.

## Критерии готовности

1. Перестановка блоков не запускает TTS или Whisper.
2. Изменение одного ЗК создаёт ровно один новый WAV.
3. Новый СНХ существующего спикера не запускает Whisper повторно.
4. Новый спикер запускает Whisper только для его просмотровки.
5. Удалённые блоки остаются доступными в старой версии.
6. Подтверждённые ручные `In/Out` не теряются.
7. Split/merge отображаются до запуска обработки.
8. Новая сборка создаёт отдельный XML и sequence.
9. Пользователь заранее видит объём повторной работы и ETA.
10. Любую подтверждённую редакцию можно повторно экспортировать без пересчёта.

## Риски

- одинаковый текст может встречаться в нескольких местах или редакциях;
- сильно переписанный блок может ошибочно выглядеть как новый;
- split/merge нельзя всегда определить автоматически;
- переименование медиа не должно ломать content identity;
- изменение модели Whisper/TTS намеренно инвалидирует соответствующий кэш;
- удаление файла с диска не должно удалять историю его использования;
- ручные решения должны иметь приоритет над автоматическим diff.

Все неоднозначные случаи переводятся в review. Система не должна экономить
время ценой незаметной потери или замены уже подтверждённой монтажной работы.
